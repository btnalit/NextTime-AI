fix(kernel): correct default WorkerDefinition capabilities and two test bugs (CI-caught)

CI's Postgres-backed test job caught three real bugs the local (no-DB) run couldn't:

- application/task/handle-mint.ts: `defaultWorkerCapabilities` was returning the *unfiltered*
  worker ceiling (including execute-class names) for a WorkerDefinition that declares no
  `capabilities` of its own. Since `computeChildHandleScope` rejects the whole call when an
  execute-class capability is missing from the caller's scope, this made every plain,
  capability-less WorkerDefinition uninvocable by an entry Handle -- the common case, and the
  one the S2 acceptance flow depends on most. Fixed to filter out execute-class names (matching
  the documented "least privilege" intent in packages/shared/src/worker-definition.ts), and
  moved into handle-mint.ts so invoke.ts's real minting path and service.ts's findWorkers dry-run
  can no longer independently disagree on the default (they previously did: invoke.ts defaulted
  to the full ceiling, service.ts defaulted to no capabilities at all).
- application/task/reaper.integration.test.ts: the waiting_approval routing test's raw SQL
  transitioned an action_requests row to 'approved' without an approval_decision_id, violating
  that table's own I11 CHECK constraint. Switched to 'denied', which carries no such requirement
  and is an equally valid "left pending_approval" resolution for exercising the router itself.
- interfaces/http/capability-route.test.ts: "a registered but unimplemented capability -> 501"
  used set_quota as its example -- this PR just gave it a real handler. Swapped to issue_handle
  (still unimplemented), the same fix already applied to application/gateway/dispatch.test.ts's
  analogous test.
