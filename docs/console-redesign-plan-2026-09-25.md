# 控制台产品化重构方案（2026-09-25）

> 起因：维护者对控制台的判断——易用性、产品化、美观三项都远未达标；具体事故是"在对话里让 agent 列出 RagFlow 知识库，
> 它做不到，也不知道该去控制台哪里授权"。W1–W5 按审计清单逐页修了约 98 项，但没有从"一个人要让 agent 用上一个系统"
> 这件事出发走通整条链路，产品形态本身没变。本方案先把授权链路的根因查清、把模型里的陷阱去掉，再重做信息架构与页面。
>
> 依据：两路只读调研（授权与能力链路审计、产品设计审查，均为 Sonnet 子代理）+ 主会话对关键代码与生产结构数据的核对。
> 本文取代 `convergence-plan-2026-09-25.md` 里 W6 / W7 的排序（§8）。

## 1. 现状：用户要做成一件事，要过几关

"在对话里说一句'列出 RagFlow 知识库'，agent 直接调用 `kb.list`"要同时满足：

| # | 条件 | 在哪设置（控制台） | 谁能设 |
|---|---|---|---|
| 1 | 平台门实例已启用、健康 | 平台 · 集成 | 平台管理员 |
| 2 | 门在本工作区启用 | 治理 · 系统接入 | owner / operator |
| 3 | 门的 Operation 已发布（`kb.list` 是 `mode: observe`） | 系统接入 / 能力目录 | owner |
| 4 | 成员被授权这个门（`capability_grants`） | 治理 · 访问（只有 owner 看得到） | owner |
| 5 | 成员的 AgentProfile 没把这个门排除掉 | 使用 · 我的智能体 | 成员（策略允许时）/ owner |
| 6 | 入口 agent 的 Handle 范围 = 4 ∩ 5，每轮对话重算 | 无界面 | — |
| 7 | pi 会话启动时按 Handle 范围为每个只读 Operation 注册一个工具；范围变了，下一轮对话会重建入口容器 | 无界面 | — |
| 8 | 走委派时：有一个已发布、可委派、挂了这个门的 Worker | 治理 · 能力目录 → Worker | owner |

代码依据：`agent-host-runtime.ts:740-804`（Handle 范围 = 授权 ∩ AgentProfile）、`agent-profile/resolve.ts:80-89,141-145`
（清单解析规则）、`platform-extension/src/modes/entry.ts:249-274`（门工具只在 `session_start` 注册）、
`worker-supervisor/src/resident-service.ts:450-459,513-537`（Handle `jti` 变化时重建常驻容器）、
`gatekeepers/ragflow/manifest.json`（`kb.list` 为 observe / 低影响）。

八关分散在五个页面、两种角色，其中三关没有任何界面；没有一处回答"我的 agent 现在能调什么、不能调什么、差哪一步"。

## 2. 这次事故的根因

生产工作区的结构数据（只读核对）：两个门都已在本工作区启用，RagFlow 的 5 个 Operation 均已发布，成员对两个门都有授权
（docker 09-23、RagFlow 09-24）；唯一的执行 Worker `ops-runner` 只挂了 docker 门。

**最可能的根因（H1）：AgentProfile 的门清单被"冻结"。** `resolveList(explicit, available, cap)` 的规则是
`explicit ?? available`（`resolve.ts:85`）：清单为 `null`（继承）时跟随当前全部授权；一旦保存过一份明确清单，就原样生效，
**之后新增的授权永远不会进入**。表单里取消"继承"后，清单从空开始让人勾选（`AgentProfileForm.tsx:62-63`）——9-23 时
只有 docker 可选，勾上保存即成 `[docker]`；9-24 授权 RagFlow 后，入口 agent 的范围仍只有 docker，而且没有任何提示。
同一规则也作用于 Skill 与 Worker 清单（`resolve.ts:136-147`），发布新 Skill / Worker 时同样被静默排除。

核实方法（维护者在页面上即可看，不必读库）：我的智能体 → 生效配置里"系统接入"一行只有 docker 即为此因；临时解法是
编辑 → 勾上"继承" → 保存，然后新开一个对话。

排除 / 次要的原因：`kb.list` 被当成执行类而拒绝——已排除（manifest 为 observe）；门工具投影陈旧——机制存在，但下一轮对话会
自动重建容器，一天后仍失败不像是它；委派路径——没有任何 Worker 挂 RagFlow 门，本来也走不通。

**同时存在的静默失败**（都会让人误判）：

- "执行就绪"是一个全局布尔：只要有一个 Worker 能碰到任意一个门就显示"已就绪"（`execution-readiness-handler.ts:257`），
  docker 通就全绿，RagFlow 完全不可用也看不出来；而且它只衡量"委派"，不衡量入口 agent 自己能否直接调用。
- `find_operations` 对只读 Operation 不看授权一律返回（`task/service.ts:578`）：agent "看得见" `kb.list`，却没有工具可调、
  也没有 Worker 可委派；入口 prompt 对这种情况没有指引，agent 只会含糊其辞或委派给一个碰不到这个门的 Worker。
- 授权 / 配置变化与容器重建之间是 kernel → agent-host → worker-supervisor 三跳的隐式依赖，界面上看不到"工具清单何时更新"。

## 3. 目标模型（先改模型，再改页面）

原则：**"agent 能用什么"是一个派生事实，由系统算出来并解释给人看，而不是让人去五个页面拼。** 三条设计底线不变：
agent / kernel 不持凭证；触及有凭证 / 内部 / 有状态系统的动作必经审批；隔离与审计只增不减。

- **M1 AgentProfile 的三份清单改为"排除清单"语义**（待维护者决定，§7 D1）：默认跟随授权 / 已发布集合，成员只能排除，
  新授权、新发布自动生效。不变量不变：Profile 永远是授权的子集投影，永不扩权。过渡期（D1 定之前就做）：清单一旦与当前
  授权不一致，读模型与页面明确提示"新授权的 X 不在你的智能体范围内"，表单取消"继承"时以当前生效清单预填，保存前提示后果。
- **M2 一个能力可达性读模型**（扩展 `execution_readiness`，按门给出）：对每个成员 × 每个门，给出
  `enabled_in_workspace / operations_published / granted / in_entry_scope（可直接调用）/ worker_coverage（可委派）`
  以及第一个不满足的条件和"去哪修"。"已就绪"从全局布尔改为逐门状态；全局状态只作汇总。纯读、复用现有判定函数，不新增授权逻辑。
- **M3 `find_operations` 如实标注可达性**：不过滤（agent 应当知道有什么），每条结果带 `reachability`
  （`direct` / `via_worker` / `unreachable` + 原因）。
- **M4 入口 prompt 契约补一条**：可达性为 `unreachable` 时，直接告诉用户差哪一步、去控制台哪里改，不猜测、不委派给碰不到这个门的 Worker。
- **M5 对话里的"能力缺口"卡片**（第二步）：agent 依据 M3 报告缺口时，对话里渲染一张带"去修复"链接的卡片，
  让失败发生的那一刻就能看到原因和入口。

## 4. 目标信息架构

三组导航（使用 / 治理 / 平台）保留，组内重排：

- **使用**：对话（顶部一条"我的 agent 现在能做什么"状态条，点开是逐系统的能力视图）、待我审批、任务、图谱、
  **我的智能体**（先展示"能做什么 / 为什么不能"，配置降为第二块）、我的账户（机器凭证 / MCP Handle 签发移到这里）。
- **治理**：**系统与授权**（合并现"系统接入"与"访问"里的人员授权：每个系统一张卡——连接健康、Operation、谁能用、
  哪些 Worker 覆盖；"接入一个系统"向导一路走完 连接 → 发布 Operation → 授权成员 → 挂到 Worker → "去对话里试一句"）、
  能力目录（按依赖排序：Operation → Worker → Skill / Procedure → 模块）、成员（每行带能力摘要，可展开成员 × 系统矩阵）、
  审批历史与审计（按任务组织的入口，不再是四个裸表单）、模型与配额。
- **平台**：不动分组；与治理的近似页（集成 / 系统接入、模型与供应商 / 模型与配额、平台审计 / 审计）加明确的互链与范围说明。

消失的：访问页的人员授权半边（并入系统与授权）；五处重复的"执行前提"横幅（改为一处按页面过滤的状态条）。

## 5. 视觉与版式

问题主要不在令牌（`tokens.css` 已有完整的字号、间距、治理语义色），而在**页面没有组合成产品**：没有统一的页面模板、
每页多个同权重按钮、表格行没有主次、说明文字挤占首屏、768 宽时主内容被推到折叠线下、登录页从未按体系设计。做法：

- 四种页面模板：列表页、详情抽屉、配置页、概览；每页一个主操作。
- 表格行主次规则：一个加粗主标签，id / 标签 / 时间一律从属；id 永不作为主文本（审批队列现在把能力 id 当标题）。
- 说明文字默认折叠；空状态、错误统一走 kit（模型页还有裸红字 HTTP 502）；后端枚举一律经标签层翻译。
- 登录页、审计页入口、能力目录按上面模板重做。

**进度与调整（2026-09-26）**：P0 已完成并随 v0.23.0 上主机（#306 D1 / D2、#307 可达性 M2–M4、#305 D3）。P1 前端拆分只拿到小部分收益（#308 能力目录 1633 → 1528 行，#309 对话页 617 → 223 行等）：
`components/kit/*` 与 `components/ui/*` 渲染并不一致（按钮、提示、错误横幅、抽屉、引用标签实现不同；空状态、骨架屏、标签页、Toast、多行输入框在 kit 里没有），在"旧组件清单只减不增"的约束下，页面里的渲染代码挪不出去。
据此调整：**P3 先补齐 kit（按新视觉语言、不追求与旧组件像素一致），再逐页迁移——迁移即重写到 kit 上，不再先做纯拆分**；
P1 的内核拆分（`handlers.ts` / `platform-handlers.ts`）照常做。P2 的新页面直接用 kit 写，作为新视觉语言的第一批使用者。

## 7. 维护者决定（2026-09-25 全部按推荐取定）

- **D1 AgentProfile 的清单语义 → 排除清单**：默认跟随授权 / 已发布集合，只能排除，新授权、新发布自动生效（备选"门清单去掉"
  与"保持现状只加提示"未采用）。实现：governance 迁移 `0012_agent_profile_exclusions`，`set_agent_profile` 的三份清单参数改为
  `excludedSkills` / `excludedGatekeepers` / `excludedWorkerDefinitions`（线上契约变更，同 #288 的做法）。
- **D2 已有明确清单 → 重置为跟随授权并写审计**：新的排除清单一律从空开始；每个原先存过明确清单的配置写一条
  `agent_profile.lists_reset_to_follow_grants` 审计，payload 带原清单。旧列保留以便回退（`runbooks/release.md` §6）。
- **D3 机器凭证（MCP Handle）签发 → 移出"访问"**：自己的 Handle 到"我的账户"，服务主体的 Handle 到"成员"。
