# Runbook：dev-loop（AI 开发闭环：角色、交接、门、巡检）

对应交付物：`docs/state/loop.json`、`docs/state/review-map.json`、`scripts/guards/loop-ledger.mjs`、
`scripts/loop-health.mjs`、`scripts/review-route.mjs`、`scripts/pr-gate.mjs`、`scripts/host-upgrade-brief.mjs`。
前置阅读：`CLAUDE.md`、`docs/STATUS.md` §5、`docs/runbooks/release.md` §1。

这份手册写的是「这个仓库的开发流程自己怎么转」：谁做哪一步、每次换手交什么、哪条规则由机器检查、
谁定时来看。它存在的原因是 2026-11-27 的一次盘点：产出很快，收敛很慢（近 7 天一半提交是记录，
遗留一周净增三十多条，主机落后 10 个版本），而且规则大多只存在于会被截断的项目记忆里，要维护者反复提醒。
原则只有一条：**必须每次都发生的事交给脚本和 CI，手册和记忆只写机器查不了的判断**。

维护者已定的边界不因本手册改变：主机上的工作只在维护者本地的会话里做；发版由协调线程决定；
评审通过、CI 全绿的 PR 由合并线程直接合；三条设计底线不可降级（`CLAUDE.md`）。

## 1. 一条线

| 站 | 产物 | 谁做 | 门 | 维护者 |
|---|---|---|---|---|
| 目标 | 路线图任务号或遗留号（`global-roadmap-*.md`、`STATUS.md` §4） | 协调线程分派 | 没有编号不开工 | 定优先级 |
| 方案 | 新能力与 R2 / R3 的改动先出默认方案，再独立评审 | 方案线程 | 评审无阻塞项 | 被告知，可撤回 |
| 实现 | 一个线程一个分支，draft PR；正文按 PR 模板 | 作者线程 | 本地跑过相关测试 | — |
| 验证 | CI 结果挂在 PR 上 | CI | `guards` / `quality` / `test`，控制台加 `web-e2e`，发版路径加 staging | — |
| 评审 | PR 评论，首行是裁定行（§3） | `review-route` 算出的席位 | 阻塞项清零，各席位对当前 head 给出 pass | — |
| 合并 | squash 合入 | 合并线程 | `pr-gate merge` 输出 `RESULT ok` | — |
| 记录 | `STATUS.md`、`development-tasks.md` 的成批记录（§6） | 合并线程 | `loop-ledger` 守卫 | — |
| 发版 | release PR、tag、镜像 | 协调线程决定，合并线程执行 | `pr-gate release` 输出 `RESULT ok` | 被告知 |
| 上主机 | 升级简报、staging 演练、主机结果（§8） | 合并线程出简报，维护者本地会话执行 | 同一路径的演练是绿的 | 开窗口，做本人步骤 |
| 沉淀 | 教训变成守卫、测试或一行规则（§9） | 协调线程 | 新规则说明取代了哪条 | 高影响规则 |

流程的终点是「上主机并被真实使用」，不是 tag。`loop-health` 把主机落后放在报告第一行。

## 2. 角色

| 角色 | 负责 | 不做 |
|---|---|---|
| 维护者 | 目标与优先级、主机窗口与其中的本人步骤、密钥与破坏性操作 | 转述规则、提醒归档、逐个批准 PR |
| 协调线程 | 分派、并发不超过 3、发版时机、遗留分档的例外、定时巡检（§7）并处理偏差 | 手写状态文档；逐条给 P3 分档；在作者和评审之间传话 |
| 作者线程 | 实现到 CI 绿、自己找席位评审、回应评审、转 ready | 改 `review-map.json` 里 `stewardOnly` 列出的三份文档；改测试来过关 |
| 评审席位 | 按 `review-map.json` 被找到时用全新上下文看阻塞项，给裁定行 | 把每个发现都登记成遗留（§4） |
| UX 验收 | 控制台改动的旅程验收，同样给裁定行 | — |
| 合并线程 | 合并、成批记录、release PR、升级简报；是 `stewardOnly` 文档的唯一写入者 | 绕过必过检查；替席位补裁定 |

席位与线程的对应关系记在项目记忆里（线程 id 不入库）。CI、守卫和下面几个脚本是确定性的门，不是角色。

## 3. 交接：PR 是载体

换手不靠对话转述，要交的东西都在 PR 上。

1. **作者**：PR 正文按模板写，结尾有「合入后由合并线程写入的状态」一节（合并后要记什么、关哪条遗留、
   新发现按 §4 给出的档）。CI 绿后跑 `node scripts/review-route.mjs --base origin/main`，
   把风险级和席位写进正文，然后**直接**把 PR 链接和 head 发给这些席位的线程，再转 ready。不经协调线程。
2. **席位**：在 PR 上评论。评论里带一行裁定（HTML 注释，页面上不显示）：

   ```
   <!-- review-verdict seat=<席位> head=<当前 head 的 sha，至少 7 位> verdict=pass|block -->
   ```

   `block` 只用于 P0 / P1（破坏不变量、授权、可靠性，或三条底线）。P2 由席位判断是本 PR 修还是登记；
   P3 不拦合并。同一席位以最后一行裁定为准。
3. **合并线程**：`node scripts/pr-gate.mjs merge <PR>`，`RESULT ok` 才合。它检查：不是 draft；必过检查在 head 上全绿
   （路径含控制台时 `web-e2e` 必须成功）；不落后 main；路径要求的每个席位都对当前 head 给了 pass；
   `stewardOnly` 文档没被别人改；正文有交接一节。合并线程自己的记录 PR 加 `--steward`。

风险级由路径算出，作者不能自己降级：一个文件命中 R3，整个 PR 按 R3 走。

| 级 | 是什么 | 要谁看 |
|---|---|---|
| R0 | 文档 | 没有席位，必过检查绿即可合 |
| R1 | 普通功能与修复 | 所在领域的一个席位 |
| R2 | 迁移、线上契约、本体、pi 运行时、流程规则、仓库配置 | 所在领域的席位 |
| R3 | 凭据、门、脱敏、授权、隔离、CI 与供应链 | 凭据席位或主机与 CI 席位，加所在领域的席位 |

裁定行是记账，防的是漏审，不是身份认证（所有线程用同一个 GitHub 身份发评论）。裁定给出之后，
PR 上只多出「把 main 合进来」的 merge 提交时裁定仍然有效（`pr-gate` 核对这个 merge 有一个父提交在 main 上；
merge 里手改的内容它看不出来）；有别的新提交就要席位再看一次。
路由表是数据，分错了就开 PR 改 `docs/state/review-map.json`。

## 4. 遗留怎么进、怎么分档

「没在 PR 里修掉的评审发现都登记、分两档」不变（维护者 2026-11-17）。变的是谁来分、什么时候分：

1. **能在本 PR 里小改修掉的，合并前修掉，不登记。**
2. **在源头分档。** 评审或 UX 验收写下一条不在本 PR 修的发现时，同时写建议的档：
   - 「阶段内处理」：用户可见的错误行为，或削弱不变量、隔离、凭据路径、审计的；
   - 「挂起：<一句理由>」：测试缺口、注释与措辞、内部重复、没有观察到影响的性能问题。
   合并线程照建议登记，不逐条问协调线程。拿不准的登记成「开放（挂起：待分档）」（守卫只认这两档的写法），
   `loop-health` 把这种行报成「该处理」，由协调线程在巡检时定档。
3. **「阶段内处理」有上限**（`loop.json` 的 `legacy.inStageWipCap`）。超过时 `loop-health` 报「该处理」，
   协调线程重新分档，而不是继续往里加。
4. **每周新 P3 有软上限**（`legacy.weeklyNewP3Soft`）。超过后本周其余新发现默认进挂起档。
5. **同一类问题第三次出现，归并到一条「类」遗留。** 新的变体记进那一行（发现不丢），不再各占一号；
   同时开一个设计决定：是不是该换边界，而不是继续补规则。对抗输入空间无界的问题（例如按写法遮密钥）
   靠逐条登记永远追不完。
6. **关 P3 的 PR 净流入不大于零**：它的评审又发现的问题，要么本 PR 修掉，要么进挂起档。
7. 挂起档在阶段内不单独开 PR，只在别的 PR 正好改到同一处时顺手关，阶段关闭时成批过一遍。

遗留表每行五格，状态以「开放 / 部分关闭 / 待主机 / 已接受 / 已关闭 / 关闭 / 已撤销」开头；
格子里的 `|` 写成 `\|`。标着「发版前必须关闭」的开放遗留会让 `pr-gate release` 失败。

## 5. 哪些规则由机器检查

| 规则 | 检查它的 | 在哪跑 |
|---|---|---|
| 遗留表的格式、编号递增、状态词、新 P3 写明档 | `scripts/guards/loop-ledger.mjs` | CI `guards`（纯文档 PR 也跑）、`pnpm ci:guards` |
| 热文档与 `CLAUDE.md` 不超过体积上限，上限只降不升 | 同上（`docBudgets`，升上限要 `ratchet-raise` 标签） | 同上 |
| `release.md` 新的 §3 小节第一行写明主机步骤与是否要维护者本人 | 同上（`release.hostStepTagFromSection` 起） | 同上 |
| `loop.json` 里的主机版本是一个发布 tag | 同上 | 同上 |
| 路由表引用的席位都存在，R1 以上至少一个席位 | `scripts/review-route.mjs --check` | 同上 |
| 合并前：检查全绿、不落后、席位都通过当前 head、热文档没被别人改 | `scripts/pr-gate.mjs merge` | 合并线程，每次合并前 |
| 发版前：检查全绿、不落后、手写说明在、没有发版阻塞遗留、`pnpm audit` 干净 | `scripts/pr-gate.mjs release` | 合并线程，合 release PR 前 |
| 主机升级的起点、迁移数、要读的小节、演练是这条路径且是绿的 | `scripts/host-upgrade-brief.mjs` | 合并线程，出简报时 |
| 主机落后、遗留净流入、记录提交占比、文档体积、沉寂的 PR、该归档的稿子 | `scripts/loop-health.mjs` | 协调线程的定时巡检 |

没被机器检查的规则（合并顺序、发版时机、设计取舍）写在这份手册、`CLAUDE.md` 或 `release.md` 里。
项目记忆只放三类：指向仓库文档的指针、席位与线程的对应、当期状态。一条规则写进仓库后，从记忆里删掉。

## 6. 记录与归档的节奏

- **记录按批写。** 合并线程不为每个合入的 PR 单开一个记录 PR：一串连续合入之后记一次，发版前记一次，
  一天不超过两次；只有新登记的是发版阻塞项时才立刻记。`loop-health` 看记录提交在近 7 天提交里的占比
  （`cadence.recordCommitShareMax`）。
- **时间线一个波次或一次发版一行**，已关闭的遗留每次发版后移到 `status-history.md`（`STATUS.md` §5）。
- **体积上限只降不升。** `docBudgets` 每个文件两个数：`ceiling` 是守卫拦的上限；`target` 是归档后想回到的体积，
  超过它 `loop-health` 报「留意」，不拦。文档接近上限（`loop-health` 在 95% 时报「该处理」）先归档再写新的：
  已完成阶段的任务拆解移到 `docs/archive/`；主机升级之后，`release.md` 里主机已经走过的 §3 小节移到
  `docs/archive/`，原处留一行指针。归档做完，在同一个 PR 里把 `loop.json` 的上限降到新体积之上一点。
  `release.md` 只有主机升级之后才能瘦，所以它的上限留得宽；主机没升而它到了上限，是主机落后的信号：
  告诉协调线程，再用带 `ratchet-raise` 标签、经评审的 PR 抬上限，不让云端的工作停在等主机上。
- **共享文件夹**按它自己 README 的归档规则；`loop-health --project-files <目录>` 列出已发版而没归档的验收稿
  和给旧 tag 写的升级提示词。
- **项目记忆索引**不超过 12 KB；`loop-health --memory-index <文件>` 在 85% 时提醒。

## 7. 巡检：协调线程的时钟

协调线程只在被消息唤醒时行动，所以「主动」要靠定时任务。每天一次（以及每次发版后）跑：

```
git fetch -q origin --tags && git fetch -q --shallow-since=<8 天前的日期> origin main
node scripts/loop-health.mjs --github --memory-index <记忆索引文件> --project-files <共享文件夹>
```

报告每行一个结论，四种级别：「该处理」带着负责的角色和下一步；「留意」不用动；「正常」；
「无样本」表示这项没读到数据（浅克隆、没有 tag），**不等于正常**，先补数据再看。
协调线程对每条「该处理」要么当场做完，要么分派出去并说明等谁，不留到下一次巡检；没有「该处理」就不发消息。

| 报告里的偏差 | 谁 | 做什么 |
|---|---|---|
| 主机落后达到提醒线 | 协调线程 | 让合并线程出最新 tag 的升级简报，确认演练是绿的，提醒维护者一次；同一个版本不重复提醒 |
| 文档到上限的 95% | 合并线程 | 归档（§6），降上限 |
| 「阶段内处理」超上限、周新 P3 超软上限、有开放的 P1、有「待分档」的行 | 协调线程 | 定档或重新分档；第 4、5 条规则（§4） |
| 记录提交占比过高（看的是过去 7 天，改了做法也要几天才降，所以报「留意」） | 合并线程 | 记录按批（§6） |
| PR 沉寂超过 `cadence.stalePrDays` 天 | 协调线程 | 问作者线程卡在哪；等评审的直接找席位 |
| 记忆索引接近上限 | 协调线程 | 删流水和已入库的规则 |
| 有已发版而没归档的稿子 | 协调线程 | 按共享文件夹 README 归档 |

提醒线和上限都在 `docs/state/loop.json`，改它们走 PR。

## 8. 上主机

主机按大版本攒着升（维护者 2026-11-06），升不升、什么时候升由维护者决定。流程要保证的是：
他决定升的时候，东西是齐的，而且不需要有人凭记忆去数。

1. 合并线程：`node scripts/host-upgrade-brief.mjs --from <主机版本> --to <目标 tag>`。
   起点必须等于 `loop.json` 记录的主机版本。简报给出途经的版本、迁移个数与编号、要读的 §3 小节
   （按各节第一行的主机步骤行分类）和 dispatch 演练的命令。
2. 跑这条路径的 staging 演练（线程可以自己 dispatch，不带真实模型）。绿了以后用 `--staging-run <id>` 重新生成，
   简报会核对这个 run 确实是这条路径、确实是绿的。
3. 合并线程在简报第 5 节补上需要判断的要点，交协调线程发给维护者。
4. 维护者在主机检出目录的本地会话里执行，规则见 `host-upgrade-session.md`。
5. 维护者把会话最后打印的结果块贴回来。合并线程据此在一个记录 PR 里更新 `loop.json` 的 `host`、
   `STATUS.md`，并归档主机已走过的 §3 小节（§6）。

`release.md` §3 的新小节第一行写：

```
> 主机步骤：无；维护者本人：否
> 主机步骤：窗口前、应用后；维护者本人：是
```

主机步骤取「无 / 窗口前 / 窗口内 / 应用后」，可以多个；「无」单独出现。

## 9. 教训怎么沉淀

出了一次错，按这个顺序找它的去处，找到第一个能放的就停：

1. 能写成守卫或测试的，写成守卫或测试；
2. 能写成门脚本里一项检查的（`pr-gate`、`loop-health`、`host-upgrade-brief`），加一项检查；
3. 只能靠判断的，在这份手册或 `CLAUDE.md` 里写**一行**，注明日期与出处；它取代旧规则时删掉旧的，不追加；
4. 只对当时有用的，留在回顾文档里，不进规则。

「在记忆里记一条下次注意」不在这个列表里。

## 10. 还没有做的（目标，不是现状）

- **遗留表还是 Markdown。** 现在是把它当数据来检查和统计；把它拆成一条一文件或 JSON 账本、
  让 `STATUS.md` §4 由脚本生成，是一次要单独设计的迁移（编号分配、九百多个被引用的旧编号）。
- **评审裁定还没有 CI 门。** `pr-gate merge` 由合并线程在合并前跑，不是必过检查。
- **主机结果靠维护者贴回。** 云端与主机之间没有任务通道；要不要让主机上的本地会话自己开结果 PR，由维护者决定。
- **流程指标没有趋势页。** `loop-health` 给的是当下读数；要看趋势可以在任一历史提交上重跑它。
