## 0. 结论

1. **换的边界是「失败的方向」，不是再加一种认法。** 今天的规则要在任意写法里找出值的真正结尾，找短了后面的字就露出来，
   每一种新写法都是一条「露」的遗留。改成：密钥名后面的文本默认不放行，只有值以几种允许的形式收尾、
   后面跟着允许的边界时才放行其后的文本，否则从值的起点遮到行尾。值收尾收得不对的写法，从此落在多遮上，不落在露上。
   这句话的范围是「值按这几种形式读得到的写法」：值收干净以后另起一段的写法（相邻字符串拼接等，§4.2 末）和现在一样露，
   名字没被认出来的也一样（阶段 2）。
2. **总结里给的默认做法「按来源标注」不能当主路径，但有一处正相反。** 平台自己管的密钥大多靠边界挡在 agent 够不着的地方
   （Handle 不进容器、门持有连接凭据、llm-proxy 持有模型 key），不靠按写法遮。剩下要遮的是外部系统内容里的第三方密钥，
   平台不知道它们的值，没有东西可标。例外是门自己注入的凭据：目标系统把它回显出来时，今天没有任何东西挡，
   而门知道这个值，在门里按字面值遮就是主路径。这件事不属于本类，另立遗留，优先级在本类各项之前（§4.6）。
3. **验收口径同时要换。** 现在的生成器是名字、分隔符、引号的随机拼接，把任何露出的标记都算「露」。它把十几个 PR 引向了
   没有程序会输出的写法，而 YAML 里带空格的值、XML、`passphrase:`、`mysql -p…` 这些真实格式在 main 上直接露（§1.4）。
   验收改成：相对上一发布版一行不多露（沿用 300 万行对比）；真实格式语料上已知是值的字符一个不露；
   多遮的量和审计副本里被藏掉的量各有门槛。
4. **排队的各条由阶段 1 一并关掉。** 949、950、951、935、933、940、942、927、936、941 和 #1600 评审里新登记的一条
   在原型上全部遮住；#1600 已合，是最后一个按写法补规则的 PR（§6）。
5. **先叠加，后收敛。** 第一步只在现有读法的输出上多遮，绝不重新放出原文：结果里露出来的每一段，都是现有读法输出里的一段。
   「不比上一版多露」因此是构造保证，不靠测量。现有 2,622 行规则里因此变得多余的往后读与守卫，
   之后以「输出逐字相同」为门删掉（§7）。

### 1.2 脱敏今天在保护什么

按密钥从哪里来、在哪里被挡住来分：

| 密钥 | 平台知道它的值吗 | 真正挡住它的 | 按写法遮（名字规则）起的作用 |
|---|---|---|---|
| agent 容器的 Handle | 知道 | 不进容器（来源绑定，I19）；容器持有的 Handle 走 header 一律拒收，抄走一份也用不了 | 无。形状规则（JWT）仍遮 |
| 连接凭据（门） | 门知道，内核不知道 | 门持有，agent 与内核不持有。**目标系统把它回显出来时，没有任何东西挡**（见下） | 只遮存下来的、给人看的副本；agent 拿到的那份不经过它 |
| 模型 key | llm-proxy 知道 | llm-proxy 持有 | 无 |
| 平台 API key | 只存哈希 | `ntk_` 前缀的形状规则 | 无 |
| 别的会话签发的 Handle、厂商 key、PEM、`Authorization` 头 | 不知道 | 形状规则：从值本身认，不看上下文 | 无 |
| **外部系统内容里的第三方密钥**：门读回来的配置文件、环境、日志；容器里工具读到的同类内容；人贴进对话的 | **不知道** | 没有边界能挡：agent 要靠这些内容干活 | **唯一的手段** |

三点由此得出：

- **名字规则保护的只剩最后一行。** `secret-values.ts` 开头的说明仍把「容器里的 Handle」写成主要理由，设计文档 §7.3 已改
  （「Handle 现已不进容器，脱敏保留，对付的是其他会话里拿到的凭证与工具输出里的第三方密钥」）。代码注释落后于设计文档，
  属于语义漂移，实现时一并改。〔读〕
- **它防的是意外，不是对手。** 同一段注释写明：先编码（base64、一个字一行）的输出遮不住，蓄意外泄要靠边界解决。
  能构造 `token="x"y"<密钥>"` 这种写法的一方，同样可以先编码。针对人为构造写法的加固，在已声明的威胁模型下没有安全收益。〔读〕
- **观察类调用的结果原样交给调用它的 agent**（另存的 Observation 和给人看的副本是遮过的）；执行类调用的结果，
  agent 拿到的就是审计行里遮过的那份。〔读，`gate-observation.ts` 与 `request-action-handler.ts` 的说明〕所以第三方密钥进 agent 上下文这件事，按写法遮本来就不拦，它拦的是
  「内核把 agent 产出的东西交给人、写进库」这一步。
- **门自己注入的凭据被回显，是「够不着」这一层的缺口。** HTTP 门把凭据放在请求头里（`gatekeeper-base` 的 `credentialHeaders`），
  把响应体原样作为结果返回；`gatekeeper-base` 里没有任何一处在结果离开门之前按字面值遮掉它自己注入的凭据。
  目标系统回显请求头、在错误体或自省接口里带出 token 时，这个凭据直接进调用它的 agent 的上下文，再随对话发给模型。
  挡在中间的既不是名字规则（不经过），也不是「不进容器」（管不到回显）。〔读，凭据席位评审 #1614 时指出，本次核对了代码〕处置见 §4.6。

### 1.3 为什么逐条补追不完

1. **问题本身没有边。** 名字规则要用正则在 shell、JSON、JSON 里的 shell、YAML、源码混写的文本里判断值在哪里结束。
   这些文法互相嵌套，一行文本常有不止一种合法读法。每修一种读法，就有一种相邻写法在另一种读法下露出来。
2. **失败方向是露。** 值读短了，后面的字照原样放出。于是每个新变体都落在「削弱凭据路径」上，按分档规则进「阶段内处理」。
3. **一条规则要在四种读法下一致。** 整段、实时流（任意切点）、存量改写、v0.70.0 下限，再加幂等（再读一遍不变）。
   近几个 PR 的评审篇幅大半花在这四者的对齐上（`placeIn`、`repairSplitQuotedMasks`、扣留长度、计数），不在漏不漏上。
4. **验收没有真值。** 生成器随机拼接名字、分隔符、引号和一个标记，标记露出就算「露」，不问它是不是任何一对的值。
   评审用的生成器放在各线程容器的临时目录里，不在仓库，PR 里的数字别人无法重跑。〔读，项目记忆中的评审方法〕
5. **「名字算不算密钥名」有两份定义。** 结构化字段用 `@nexttime/shared` 的 `namesASecretField`（强词在名字里任何位置都算），
   纯文本用 `secret-values.ts` 自己的词表（只看最后一个词）。〔测〕`{"passphrase": "…"}` 作为字段被遮，
   同一段文本里的 `passphrase: …` 不遮；`secret_key_base`、`passwordx`、`tokenValue` 同样是字段规则算、文本规则不算。

|---|---|---|

| XML | `<password><密钥></password>`、`<add key="Password" value="<密钥>" />` | 原样 |
| 命令行惯用法 | `mysql -u root -p<密钥> db`、`sshpass -p <密钥> ssh host`、`curl -u admin:<密钥> …`、`redis-cli -a <密钥>` | 原样 |

一周的评审力量花在随机拼接出来的写法上，而配置文件里最常见的写法没有人测。
这不是哪个 PR 的疏忽，是验收口径把工作引到了那里。

## 2. 领域模型（只列本次涉及的）

| 概念 | 是什么 | 现状 |
|---|---|---|
| 平台管的密钥 / 第三方密钥 | 前者的值平台某个进程知道；后者在外部系统的内容里，平台不知道 | 代码不区分，同一套规则 |
| 形状规则 | 从值本身认的规则（JWT、PEM、前缀 key、`Bearer`、URL 密码）；没有「值到哪里结束」的问题 | 稳定，不在本设计范围 |
| 名字规则 | 靠前面的名字和分隔符认值的规则（env 行、`name: value`、`--flag`、JSON 对） | 本设计的对象 |
| 现有读法（下文记 E） | 今天的名字规则与形状规则合起来读一段文本的结果，含 v0.70.0 下限 | 保留，阶段 1 一行不删 |
| 收尾检查（下文记 T） | 本设计新增的一读：对每个「密钥名 + 分隔符」核对值是否干净收尾（§4.2） | 没有 |
| 干净收尾 | 值以允许的形式闭合，且后面是允许的边界 | 没有这个概念：只有「读到哪算哪」 |
| 行尾遮 | 收尾不干净时，从值的起点遮到这一行结束 | 只有 `Authorization` / `Cookie` 头这样做 |
| 行尾掩码 | 行尾遮写下的掩码。和普通 `[redacted]` 分得开，带上藏了多少字符 | 没有 |
| 合成 | E 与 T 怎么并成一个输出（§4.3） | 没有 |
| 读法 | 同一文本的四种读：整段、实时流、存量、下限 | 四者各有例外 |
| 收尾未证明的行 | 已存的行里，掩码后面的文本过不了收尾检查的。可能是密钥残留，也可能只是旧版本遮得不齐 | 没有：清洗报告只有一个数 |
| 真值 | 生成一行文本时就知道哪些字符是密钥值 | 没有：生成器只放一个标记 |

不变量（实现要用机制保证的）：

- **I-R1 单调。** 任何文本，新版本露出来的每一段，都是上一发布版输出里的一段，顺序不变。
  （现有：v0.70.0 下限。阶段 1 的合成按字面满足它，见 §4.3。）
- **I-R2 失败方向。** T 认出一个名字以后，它的值后面同一行的文本，只有在值干净收尾时才放行；认不准就多遮。
  范围是值按 §4.2 的几种形式读得到的写法；它不保证值收干净以后另起的一段。（新增，本设计的核心。）
- **I-R3 读法一致，分两层。**
  (a) T 单独：整段与任意切点的实时流遮住的相同；输出再读一遍不变。门槛是 0 行不同。
  (b) 合成后的输出：是 T 的不动点（再用 T 读一遍不变）；实时流与整段不同的行、再读一遍还变的行，不多于上一版。
  E 自己今天就有流与整段不同、再读还变的行，本设计不承诺把它们清零，只承诺不增加。
- **I-R4 名字一处定义。** T 认名字只用一个函数，整段、实时流、存量都调它。阶段 2 把它和字段规则对齐成一个判断。
- **I-R5 验收有真值。** 计入「露」的字符，是生成时已知为某一对的值的字符。
- **I-R6 多遮可见。** 行尾遮照常计入 `redactedValues`，另有单独的计数；写下的行尾掩码带字符数。
  清洗报告、审批上的「已隐藏 N 个值」照常出现。读审计的人看得出这里藏的是一段，不是一个值。

## 3. 候选边界与取舍

| | 做法 | 结论 | 理由 |
|---|---|---|---|
| A | 按来源标注：密钥进入系统时带标记，输出按标记（字面值）遮 | **对第三方密钥不作主路径**；对门自己注入的凭据是主路径，另立遗留（§4.6） | 只对值已知的密钥有效。第三方密钥没有可标的值；而且字面值来自同一次识别，值读短了，登记的字面值一样短 |
| B | 结构化、白名单输出：给人看的只放声明过的字段，不放自由文本 | **只在已有结构处用**（现状已如此） | 工具结果与回复的自由文本就是可追溯性的产品价值。JSON 能解析时已按字段规则精确遮，那里没有值的结尾问题 |
| C | **值的结尾改成白名单：证明干净才放行，否则遮到行尾** | **采用** | 把无界的「找结尾」换成有限的「核对收尾」；收尾不对的写法失败方向从露变成多遮；规则只增不减，符合第三条底线 |
| D | 维持现状，只把新变体并进一行「类」遗留 | 不采用为终态 | 队列里还有 10 条，每条一个 R3 PR；并号只是少占编号，流入不变 |
| E | 去掉名字规则，只留形状规则 | 不采用 | 配置文件里的口令会原样显示，比现在少遮，违反「只增不减」 |

C 的本质是 B 的思路用在值的边界上：不是「认出是值的才遮」（黑名单），而是「密钥名之后，认出是干净结尾的才放」（白名单）。

## 4. 目标方案（Target Architecture）

### 4.1 四层，各管各的

| 层 | 挡什么 | 本设计动不动 |
|---|---|---|
| L0 够不着 | 平台管的密钥不进 agent 与内核进程 | 不动。只改 `secret-values.ts` 开头那段过时的理由。它有一处缺口（门回显自己的凭据），由 §4.6 的遗留补 |
| L1 结构 | 能解析成结构的内容按字段名遮，值是什么样都遮 | 不动。阶段 2 让文本规则与它共用名字判断（I-R4） |
| L2 形状 | 值本身可认的密钥 | 不动 |
| L3 名字规则 | 自由文本里靠名字认的第三方密钥 | **改：加一读 T，干净收尾才放行**（§4.2），与现有读法合成（§4.3） |

### 4.2 规则：干净收尾，否则行尾遮

**名字怎么认（阶段 1b 就定下来，T 的三种读法共用一个函数）。**
一个名字加分隔符：分隔符是 `:` `=` `=>` `:=`，两边各至多 8 个空白；`--flag` 后面是 `=` 或空白。
名字两侧没有引号时，用文本规则现有的判断（`namesASecretValue`）；任一侧带引号（含转义的引号）时，
文本规则或字段规则（`namesASecretField`）有一个认就算。这比 E 的各条规则合起来略宽：多认 `=>` 与 `:=`，
多认只有一侧带引号的键、带引号的键后面跟 `=`。E 自己的规则照旧用各自的认法，它们只参与合成。
没有引号的名字要不要也用字段规则（`passphrase:` 等），留到阶段 2，那一步要单独量多遮。

**值是下面几种形式之一，才可能算干净收尾。** 从分隔符后面第一个字符起读：

- 掩码：一个 `[redacted]` 或行尾掩码（可带一对引号）。
- 引号值：`"…"` 或 `'…'`，里面的 `\x` 作为一个整体读，到第一个没被转义的同种引号为止。
- 转义引号值：`\"…\"`（1 到 7 个反斜杠），由同样长度的一串收尾，中间没有别的引号。
- 容器：`{…}` 或 `[…]`，括号在这一行里配平，里面的字符串整个读过。整个容器算一个值。
  `{` 或 `[` 后面这一行没有别的字（容器写成多行）时不算值，里面各行各自读。
- JSON 标量：数字、`true`、`false`、`null`，后面紧跟 `,` `}` `]`。它不是 T 要遮的（E 遮的照旧）。
- 裸值：一段不含空白、引号、反斜杠、反引号、`&` 的字符。`,` `;` `|` `)` `]` `}` `>` 都算在值里，和 E 今天读裸值的范围一致。

**然后核对三条：**

1. **值不超过长度上限 L**（含引号）。L 是规则里的常数，整段与实时流用同一个数，取值使
   「名字 + 分隔符 + L + 第 3 条要往后看的字符」不超过 `STREAM_HOLD_MAX_CHARS`（原型用 3,584）。
   超过的不算干净收尾。这样整段和流对一个很长的干净值结论相同，不靠流的扣留上限来定。
2. **值里没有起另一对。** 引号值、转义引号值的内容里不出现 T 认的名字加分隔符；裸值本身不是这样一个名字或 `--flag` 的开头；
   内容不是「掩码加别的字」。
3. **值后面是允许的边界。** 允许什么，按值的形式分两张表：
   - 引号值、转义引号值、容器、掩码之后：行尾；空白；`,` `;` `&` `|` `)` `]` `}` `>` `.`；反引号；全角标点。
   - 裸值之后：行尾；空白；`&`；反引号。
   - 两张表前面都可以先跟一个或几个掩码（E 自己会写出 `"[redacted]"[redacted]` 这样的文本，里面没有字符）。
   - 两张表前面都可以先跟外层字符串的收尾引号（可带转义），条件是**这一行在名字之前确实开过这样一个字符串**：
     同一种引号、同样多的反斜杠，在名字之前出现奇数次，本行已读过的值不计入。没有这个证据的引号不算外层收尾
     （`docker run -e TOKEN=ab" cd<密钥>" img` 里的 `"` 就不算）。
   - 边界之后至多 8 个空白内不是分隔符（`:` `=` `=>` `:=`）。是的话，刚读的那个「值」其实是下一对的键。

三条都满足：只遮这个值（引号留着），从边界往后照常读。**任何一条不满足，或者值不是上面任何一种形式：
从值的起点遮到行尾，写成一个行尾掩码。**

再加一条按格式读的：**行首的一对**（`name: value`、`NAME=value`、`export NAME=value`、`- name: value`）且是裸值、
后面这一行还有别的字时，值算到行尾。YAML、`.env`、INI 里行尾之前都是值。它不在 ` #` 处停：
INI（`configparser` 默认不认行内注释）和 systemd 的 `EnvironmentFile` 里 ` #` 后面仍是值，停下来会露，多遮的只是一段注释。

**行尾掩码。** 写成和 `[redacted]` 同一个前缀、看得出是行尾遮、带上被藏的字符数的形式（例如 `[redacted +214]`，
具体写法阶段 1b 定，要过词表守卫与线上契约）。要求：所有认 `[redacted]` 的地方（E 的「已经遮过」判断、T 的掩码值、
控制台的显示）都认它；再读一遍不变；计数单列（`redactedTails`），同时照常计入 `redactedValues`。
它暴露的是被藏那一段的长度，不是密钥的长度；审计副本要靠这个数知道这里少了多少（§9）。

几点说明：

- **「行」是被读的那个字符串里的一行。** 工具结果是 JSON 文本时，是解码后的字符串值里的一行（沿用遗留 916 的解码读法）。
  没被解码的文本里字面的 `\n` 不算行尾，行尾遮会一直遮到真正的换行：多遮，方向正确。
- **每张边界表的每一项都是一次「这里放行」的决定。** 「不比现在多露」不靠这两张表保证，靠合成（§4.3）：
  T 只在 E 的输出上多遮。表决定的是 T 自己多遮多少。往表里加一项、或改裸值在哪里停，要说明理由并过 §8。
- **T 再读自己的输出不变，是量出来的性质，不是证出来的**：行尾遮写下的是 `name=` 加行尾掩码，再读时值是一个掩码、
  后面是行尾。原型在 124 万行生成器文本上 0 行不同（§5）。它是 §8 的一道门。
- **计数。** 一次行尾遮算一个值。用到计数的地方只看是否大于 0（§3.220 已核对过）。
- **线性时间。** 每一条检查都是从值的起点向右的一次扫描，值里找名字只在名字可能起头的位置试，和现有规则同一种写法。

**三条都满足仍然会露的写法**（main 今天同样露，所以不是回退；它们是 I-R2 范围之外的）：〔测，凭据席位给的例子〕

- 相邻字符串拼接：`password = "ab" "cd<密钥>"`（Python、C），`const password = "ab" + "cd<密钥>";`。
- 引号值后面的 `.` `,` 等紧接着字：`password="ab".cd<密钥>`、`密码 password="ab"，<密钥>`。
- YAML 流式映射里带逗号加空格的值：`{user: u, password: ab, cd<密钥>}`。

第一种可以再加一条「引号值后面 8 个空白内不是引号或 `+`」，原型上代价是仓库文本多约 80 行行尾遮（§5）。
它会把 `cmd --password "x" "file name"` 这样正常的命令行也遮到行尾，所以不放进阶段 1，留给阶段 2 连同真实格式语料一起定。

### 4.3 合成，与四种读法怎么对齐

**合成（整段）。** 对一段文本：

1. E 照今天的样子读整段（含 v0.70.0 下限），得到它保留了原文哪些段、遮了哪些段。
2. T 读**原文**（不读 E 的输出），逐行得出要多遮的段：干净收尾的值、从某个位置到行尾。
3. 结果是 E 保留的段里去掉 T 要遮的部分。被遮的一段连同紧挨着它的掩码写成一个掩码；到行尾的那一段写成行尾掩码。
   实现上复用 `withFloor` 已有的做法：把 T 当成又一种读法，它保留的段由第 2 步给出。
   结果里露出来的每一段，都是 E 的输出里的一段，按原来的顺序。所以 I-R1 按字面成立，
   `placeIn` 放错位置（遗留 946）也只会多遮。`withFloor` 里「两种读法输出相同就直接返回」的快路径不能把 T 跳过去。
4. 对第 3 步的结果再用 T 读一遍，取它的输出。少了这一步，结果不是 T 的不动点：E 遮的范围和 T 认的值的范围不一样时
   （例如 E 把值后面的 `&` 一起遮了），合成出来的文本里掩码后面紧贴着的字变了，再读一遍会判成行尾遮。
   原型上不加这一步每 10 万行有 1 到 7 行再读会变，加上是 0（§5）。T 只会多遮，所以这一步不影响 I-R1。
   阶段 1b 可以换成等价的一遍做法（例如把「E 与 T 对值的范围看法不同」直接判成不干净），门槛是 §8 的同一行。

T 读原文而不是读 E 的输出，是有意的：E 有时会把一个没收干净的值连同后面紧贴着的字一起遮掉，
读 E 的输出就看不出那里原来收得不干净。阶段 3 要删 E 的这类往后读，也要求 T 的结论不依赖它们。

**实时流。** 原型只做了整段；下面是规格，阶段 1b 实现后由 §8 的门核对。记现有的流读法为 S。

- T 对一对的结论需要看到：值闭合，或超过 L；边界；再往后至多 8 个空白加 2 个字符。
- 一对的结论没出来时，从它的名字起的文本不放出（S 今天对「名字后面的值还没到齐」已经这样扣）。
- 放出一段时，用的是整段的同一个合成函数，作用在「E 与 T 的结论都已定」的那一段上，不是在 S 输出的字符串上再加工。
- 判定行尾遮以后：放出到值起点为止的部分；这一行剩下的字符照常喂给 S（它的扣留、跨过换行的匹配和整段一致），
  但它们的输出丢弃；S 在这一段里起头、跨过换行的掩码并进行尾掩码。行尾掩码在换行到达或流结束时放出（那时才知道藏了多少字符）。
- 两个上限怎么合：T 自己至多扣「名字 + 分隔符 + L + 往后看的字符」，按 L 的取法不超过 `STREAM_HOLD_MAX_CHARS`。
  S 的扣留可能起得更早；合起来超过 `STREAM_HOLD_MAX_CHARS` 时，按 S 现有的做法处理（放出一个掩码并暂停到下一次刷新），
  它遮的不比行尾遮少。
- 第 4 步的再读，在流里是合成输出后面再接一级同样的 T，上限相同。
- 对抗写法下「整词扣住、每块重读」的耗时（§3.220 的 3 倍）在行尾遮的行上消失：剩下的字符不再扣留。

**存量。** 分清两个数，清洗报告里分开写：

- **密钥残留**：现有存量读法会改的行。口径不变（「遮完和原来不同才算」），改写的三类照常改写。
- **收尾未证明**：现有读法不改、T 会多遮的行（原型上 98% 是行尾遮，其余是 T 多认出的值）。八类都只计数，不改写（D3）。
  它的意思是「掩码后面的文本过不了收尾检查」，不是「这里有密钥」。只计数的五类里，以前版本留下的 `TOKEN="[redacted]"<密钥>y`（遗留 950、951）
  落在这里；E 把值遮了一半、后面是无害代码的行（`TOKEN = [redacted]'hex');`）也落在这里，T 分不出这两种，
  因为它们的形状和遗留 949 的残留（`"[redacted]"b'<密钥>`）是一样的。
- 量级〔测〕：仓库文本里 main 遮过东西的 5,137 行，再用 T 读 main 的输出，998 行会变（19%），其中 983 行是行尾遮。
  按文件分：脱敏自己的测试 1,623 行里 755 行，文档 376 行里 113 行，其余 3,138 行里 130 行（4.1%）。
  随机拼接的生成器文本上是 51%–95%。所以这个数在主机上会不小，它只能当「去看一眼」的信号，不能当密钥数。
- 两条验收：各发布版写下的、已经遮好的行（掩码后面是允许的边界，含 `"[redacted]"[redacted] y`、
  `TOKEN=\"[redacted]\"[redacted] y`、`'[redacted]'[redacted] y` 这几种 E 自己会写出的形式）两个数都计 0；
  阶段 1 自己写出的行再读一遍不变（否则下次升级会把自己写的行计进去，`auditPayloads`、`auditResults` 存的就是当时遮过的副本）。

**下限。** `withFloor` 与冻结的 v0.70.0 读法保留到阶段 3。

### 4.4 验收口径与遗留怎么登记

验收改成四条，都能在仓库里重跑：

1. **不比上一发布版多露**：沿用现有做法，各生成器乘各种子共 300 万行，逐行比遮住的字符，由遮变露 0 行。
   整段、实时流（与上一版的流在同样切点比）、存量各算一遍。合成按构造满足它，这一条用来查实现有没有写错。
2. **真实格式语料上真值不露**：语料由文法生成（一组键值对的抽象表示，按 `.env`、YAML、INI、JSON、JSON 写在字符串里、
   shell 赋值与 `--flag`、PHP 与 Ruby 的 `=>`、连接串、XML 等序列化），生成时记下每个值的位置；
   断言这些位置上的字符全部被遮。每加一种格式，是一个有限的小 PR。
3. **多遮有预算**：普通文本语料（仓库自己的文本、单行 JSON 当原始文本读）上与上一版读得不同的行数和多遮的字符数写进 PR，
   超过约定比例要说明。
4. **藏掉的量看得见**：前三条只量「露」，量不到「藏」。审计副本和容器里工具调用的记录被行尾遮藏掉多少，
   靠行尾掩码的字符数和单列的计数，§8 有自己的一行。

登记规则随之改（写进 `dev-loop.md` §4，取代第 5 条里「新的变体记进那一行」的开放式写法）：

- 上面第 1 条被打破的，是回退，照旧是发版阻塞。
- 真实格式语料上露的，登记进「类」这一行，档是「阶段内处理」，修法是给语料加格式、给名字文法加一项。
- **只在随机拼接的生成器上露、任何一种列入语料的格式都写不出来的，不登记、不单独修**：行尾遮之后这类应当只剩
  「名字没被认出来」的，它们按第二条的格式清单推进，不按写法推进。
  「任何一种列入语料的格式都写不出来」由凭据席位或内核席位在评审里判定，不由作者自己定档。
- 只多遮的，写进「类」这一行的多遮清单，档是「挂起」，攒到有可读性投诉时一起调允许的边界表。

### 4.5 不做的，和留到以后的

- **不做按来源分档的规则**（工具输出一套、模型回复一套）。行尾遮只在异常行上触发，实测量小（§5），一套规则够用。
  出现「模型回复里正常的句子被整行遮掉」的真实反馈时再议。
- **不做会话内字面值接力**（在工具结果里认出的值，登记下来，在随后的回复里按字面值遮）。它能补上
  `the password is <密钥>` 这种句子，但要新增一份有生命周期的会话状态，短值会误伤正文。进入条件：主机上观察到这类外露。

### 4.6 门回显自己的凭据：另立遗留，和本设计的关系

**事实**（§1.2 末）：门注入的凭据被目标系统回显时，原样进调用它的 agent 的上下文。

**它不属于本类，处置也相反。**

| | 本类（值读到哪里停） | 门回显自己的凭据 |
|---|---|---|
| 密钥是谁的 | 第三方的，平台不知道值 | 平台管的，门知道值 |
| 露给谁 | 人看的副本、存下来的行 | agent 的上下文，随后是模型 |
| 碰到哪条底线 | 第三条（审计与隔离只增不减） | 第一条（agent / 内核进程不持凭证） |
| 该在哪里挡 | 内核读文本的那一层，按写法 | 门里，结果离开门之前，按字面值 |
| 认法 | 名字加收尾 | 字面值，含常见编码（URL 编码、`Basic` 的 base64 等） |

本设计的 T 和 E 都帮不上它：它们作用在存下来、给人看的副本上，agent 拿到的那一份不经过它们；
就算经过，回显里的 token 没有密钥名在前面时名字规则也不认。反过来，那条遗留也不解决本类：第三方密钥没有字面值可用。
两边互不依赖，改的也不是同一批文件（`gatekeeper-base` 与内核的脱敏），可以并行。

**处置。** 协调线程 2026-11-27 定：另立一条遗留「门在结果离开前，按字面值遮自己注入的凭据（含常见编码）」，
档是「开放（阶段内处理）」，优先级在本类各项之前，因为它碰的是第一条底线。凭据席位评估做法。
那条遗留自己要定的，这里只列出来不展开：遮哪些值（这一次调用实际注入的）、哪些编码、多短的值不按字面遮、
大响应体分块时值跨块怎么办、遮了几处要不要报给内核记审计。llm-proxy 对模型 key 已有按真实值精确替换的先例
（凭据席位指出，遗留 165）。

- 随机拼接上合成仍露的行，绝大多数是标记前面根本没有被认出的一对（生成器的名字有一半文本规则不认，或者值是空的）。
  这正是 §1.3 第 4 条：这些行里标记是不是「值」没有真值。
- 「合成露而 main 遮」是 0，是因为合成只用 E 的输出里的段。第一稿的原型（先 T 后 E）不是 0：
  我的生成器上每 10 万行 4–53 行，凭据席位的生成器上最多 159 行；那个顺序不用了。
- 仓库文本上不同的 2,008 行里，1,187 行在脱敏自己的测试文件里（对抗写法的用例），189 行在文档里（多是描述这些写法的句子），
  其余 86.6 万行里是 632 行（0.073%）：行尾遮 136 行，按行首格式读到行尾 166 行，剩下的是多认出的值（带引号的键、容器）。
  行尾遮的典型是代码里引号后面接着表达式的写法（`const token = require('fs').readFileSync(…)`、
  `` `export API_TOKEN="${SECRET}"\nok` ``）和对象键后面的箭头函数（`rotate_api_key: () => {`）；按行首格式读到行尾的典型是
  `privateKey = (await …).privateKey`、`GH_TOKEN: ${{ secrets.… }}`，main 也已经遮了它的第一个词。
- 单行 JSON 当原始文本读（`chat.stream`、Turn 报告、Decision、解析不了或被截断的 JSON 走这条路）：不同的 211 行都是
  密钥名下面的值是一个对象或数组（JSON Schema 里的 `"password":{"type":"string"}` 这类），整个容器写成一个掩码，后面的兄弟字段照常显示。
  没有容器这一种值的形式时，同样的语料有 211 行从那里遮到行尾，可见字符少 18%。被截断的 JSON 里没闭合的那个值会行尾遮，那是对的。
- 各条检查各自的代价（仓库文本上多出的不同行）：「边界之后不是分隔符」37 行；「外层收尾引号要有证据」18 行；
  候选的「引号值后面不是引号或 `+`」约 80 行（未采用）。

## 9. 风险与代价

- **多遮是真实的代价，不是免费的。** 异常行从值往后整段不可见。
- **被藏掉的是审计副本，不是审批人看到的参数。** 审批人看到的参数是原文，控制台只按字段名遮
  （`action-request-wire.ts` 的 `params: row.params`，`web/src/lib/format.ts` 的 `redactSensitive`）；行尾遮落在审批上，
  只是让「已隐藏 N 个值」的二次确认多触发。〔读，凭据席位指出，本次核对了代码〕按名字规则遮的是每次调用参数的审计副本和容器里工具调用的记录，
  后者是事后查 agent 在容器里跑了什么的唯一一份。一行 `export TOKEN="x"y; curl … | sh`，今天的记录还看得到 `curl …`，
  行尾遮之后看不到。写出这种行的可以是被外部内容注入的 agent。今天把命令写进一个密钥名的值里已经能藏
  （`TOKEN="curl … | sh"; eval "$TOKEN"`），行尾遮把能藏的范围从值扩大到行尾。这碰到第三条底线里的「审计只增不减」，
  所以行尾掩码必须和普通掩码分得开、带字符数、计数单列（§4.2、§8）：读审计的人至少知道这里藏了一段、多长，
  可以把「带行尾掩码的调用」当成一类要看的事件。它不能让人看到被藏的内容；要看原文只有回到容器或目标系统。
- **行首格式读到行尾会多遮说明文字。** `token: used for authentication` 这样的行会从 `used` 遮到行尾
  （现在只遮 `used`；中文说明因为没有空格，现在就已经整段遮）。量在 §5：86.6 万行里 166 行。
- **「收尾未证明」这个数会偏大。** 它在主机的清洗报告里会比「密钥残留」大得多（§4.3），容易被读成有这么多密钥。
  报告里的文字要写明它的意思，并且分开两个数。
- **两张边界表会被不断要求放宽。** 每放一项都可能重新打开一种写法。约束：加项必须过 §8，并在表里写明理由。
- **「不登记人为构造的写法」可能被读成降低标准。** 它不降低任何已有的遮蔽（I-R1 不变），只是不再把无界的输入空间当待办。
  这一条需要维护者明确同意（D1）。
- **阶段 3 的删除有回归风险。** 所以它排在最后、过两道门，并且可以不做。
- **实时流的合成只有规格，没有原型。** §4.3 的几条是按 `secret-stream.ts` 现有结构写的，1b 实现时可能要调整；
  调整以 §8「合成的一致」那一行为准。
