# 脱敏类遗留换边界：密钥名后面的文本，证明值收干净了才放行（设计决定）

> 状态：默认方案，待「凭据、门与脱敏」「内核」两个席位独立评审；§10 的 D1–D4 待维护者拍板，每项有不回复时的默认做法。
> 本文只出设计，不改运行时代码。
> 起因：`docs/runbooks/dev-loop.md` §4 第 5 条。「值读到哪里停」这一类在遗留 937、939、948 之后又出了 949–953
> 和 #1600 评审里新登记的一条，早过第三次；#1600 的作者与凭据席位都建议归并成「类」并开换边界的设计决定。
> 上位文档：`graph-ai-middle-platform-design.md` §7.3（来源绑定、模型与工具输出的密钥脱敏）、
> `runbooks/release.md` §3.216–§3.221（每次补规则的读法与代价）。
> 标注：〔读〕读代码或文档得出；〔测〕本次在 main（e0f0ee3）上跑出来；〔推〕推断。

## 0. 结论

1. **换的边界是「失败的方向」，不是再加一种认法。** 今天的规则要在任意写法里找出值的真正结尾，找短了后面的字就露出来，
   每一种新写法都是一条「露」的遗留。改成：密钥名后面的文本默认不放行，只有值以三种允许的形式收尾、
   后面跟着允许的边界时才放行其后的文本，否则从值的起点遮到行尾。新写法从此只会多遮，不会多露。
2. **总结里给的默认做法「按来源标注」不能当主路径。** 平台自己管的密钥已经靠边界挡在 agent 够不着的地方
   （Handle 不进容器、门持有连接凭据、llm-proxy 持有模型 key），不靠按写法遮。剩下要遮的是外部系统内容里的第三方密钥，
   平台不知道它们的值，没有东西可标。标注只能当补充（§4.5）。
3. **验收口径同时要换。** 现在的生成器是名字、分隔符、引号的随机拼接，把任何露出的标记都算「露」。它把十几个 PR 引向了
   没有程序会输出的写法，而 YAML 里带空格的值、XML、`passphrase:`、`mysql -p…` 这些真实格式在 main 上直接露（§1.4）。
   验收改成两条：相对上一发布版一行不多露（沿用 300 万行对比）；真实格式语料上已知是值的字符一个不露。
4. **排队的 9 条里 6 条由一个 PR 按构造关掉，3 条转成「名字怎么认」的有限工作。** #1600 照常合，是最后一个按写法补规则的 PR（§6）。
5. **先叠加，后收敛。** 第一步只在现有读法之上加一条检查并取并集，「不比上一版多露」是构造保证；
   现有 2,529 行规则里因此变得多余的往后读与守卫，之后以「输出逐字相同」为门删掉（§7）。

### 1.2 脱敏今天在保护什么

按密钥从哪里来、在哪里被挡住来分：

| 密钥 | 平台知道它的值吗 | 真正挡住它的 | 按写法遮（名字规则）起的作用 |
|---|---|---|---|
| agent 容器的 Handle | 知道 | 不进容器（来源绑定，I19）；容器持有的 Handle 走 header 一律拒收，抄走一份也用不了 | 无。形状规则（JWT）仍遮 |
| 连接凭据（门） | 门知道，内核不知道 | 门持有，agent 与内核不持有 | 门的报错回显时兜底（URL 密码、名字规则） |
| 模型 key | llm-proxy 知道 | llm-proxy 持有 | 无 |
| 平台 API key | 只存哈希 | `ntk_` 前缀的形状规则 | 无 |
| 别的会话签发的 Handle、厂商 key、PEM、`Authorization` 头 | 不知道 | 形状规则：从值本身认，不看上下文 | 无 |
| **外部系统内容里的第三方密钥**：门读回来的配置文件、环境、日志；容器里工具读到的同类内容；人贴进对话的 | **不知道** | 没有边界能挡：agent 要靠这些内容干活 | **唯一的手段** |

三点由此得出：

- **名字规则保护的只剩最后一行。** `secret-values.ts` 开头的说明仍把「容器里的 Handle」写成主要理由，设计文档 §7.3 已改
  （「Handle 现已不进容器，脱敏保留，对付的是其他会话里拿到的凭证与工具输出里的第三方密钥」）。代码注释落后于设计文档，
  属于语义漂移，实现时一并改。〔读〕
- **它防的是意外，不是对手。** 同一段注释写明：先编码（base64、一个字一行）的输出遮不住，蓄意外泄要靠边界解决。
  能构造 `token="x"y"<密钥>"` 这种写法的一方，同样可以先编码。针对人为构造写法的加固，在已声明的威胁模型下没有安全收益。〔读〕
- **观察类调用的结果原样交给调用它的 agent**（另存的 Observation 和给人看的副本是遮过的）；执行类调用的结果，
  agent 拿到的就是审计行里遮过的那份。〔读，`gate-observation.ts` 与 `request-action-handler.ts` 的说明〕所以第三方密钥进 agent 上下文这件事，按写法遮本来就不拦，它拦的是
  「内核把 agent 产出的东西交给人、写进库」这一步。

### 1.3 为什么逐条补追不完

1. **问题本身没有边。** 名字规则要用正则在 shell、JSON、JSON 里的 shell、YAML、源码混写的文本里判断值在哪里结束。
   这些文法互相嵌套，一行文本常有不止一种合法读法。每修一种读法，就有一种相邻写法在另一种读法下露出来。
2. **失败方向是露。** 值读短了，后面的字照原样放出。于是每个新变体都落在「削弱凭据路径」上，按分档规则进「阶段内处理」。
3. **一条规则要在四种读法下一致。** 整段、实时流（任意切点）、存量改写、v0.70.0 下限，再加幂等（再读一遍不变）。
   近几个 PR 的评审篇幅大半花在这四者的对齐上（`placeIn`、`repairSplitQuotedMasks`、扣留长度、计数），不在漏不漏上。
4. **验收没有真值。** 生成器随机拼接名字、分隔符、引号和一个标记，标记露出就算「露」，不问它是不是任何一对的值。
   评审用的生成器放在各线程容器的临时目录里，不在仓库，PR 里的数字别人无法重跑。〔读，项目记忆中的评审方法〕
5. **「名字算不算密钥名」有两份定义。** 结构化字段用 `@nexttime/shared` 的 `namesASecretField`（强词在名字里任何位置都算），
   纯文本用 `secret-values.ts` 自己的词表（只看最后一个词）。〔测〕`{"passphrase": "…"}` 作为字段被遮，
   同一段文本里的 `passphrase: …` 不遮；`secret_key_base`、`passwordx`、`tokenValue` 同样是字段规则算、文本规则不算。

### 1.4 实测：真实格式在 main 上直接露

〔测〕把一个标记放在值的位置，过 `scrubSecretValues`，看标记是否还在。21 行真实格式，21 行都露：

| 格式 | 例子 | main 的输出 |
|---|---|---|
| YAML 值带空格 | `password: correct horse <密钥> staple` | `password: [redacted] horse <密钥> staple` |
| `.env` 值带空格 | `DB_PASSWORD=abc <密钥>` | `DB_PASSWORD=[redacted] <密钥>` |
| PHP、Ruby（遗留 927） | `'password' => '<密钥>',` | `'password' =[redacted] '<密钥>',` |
| 词表缺的名字 | `passphrase: <密钥>`、`"pwd": "<密钥>"`、`Server=db;Pwd=<密钥>;` | 原样 |
| XML | `<password><密钥></password>`、`<add key="Password" value="<密钥>" />` | 原样 |
| 命令行惯用法 | `mysql -u root -p<密钥> db`、`sshpass -p <密钥> ssh host`、`curl -u admin:<密钥> …`、`redis-cli -a <密钥>` | 原样 |
| 无分隔符的配置 | `requirepass <密钥>`、`machine … password <密钥>`、`IDENTIFIED BY '<密钥>'` | 原样 |
| 多行值 | YAML `password: \|` 的下一行、heredoc 的正文 | 只遮到第一行为止，下一行原样 |
| 句子与中文键 | `the password is <密钥>`、`密码：<密钥>` | 原样 |

其中只有 `=>`（遗留 927）在排队；没有名字的裸密钥（`mysql -p…` 这一行）是遗留 172 已接受的漏报；其余都不在遗留表里。
一周的评审力量花在随机拼接出来的写法上，而配置文件里最常见的写法没有人测。
这不是哪个 PR 的疏忽，是验收口径把工作引到了那里。

## 2. 领域模型（只列本次涉及的）

| 概念 | 是什么 | 现状 |
|---|---|---|
| 平台管的密钥 / 第三方密钥 | 前者的值平台某个进程知道；后者在外部系统的内容里，平台不知道 | 代码不区分，同一套规则 |
| 形状规则 | 从值本身认的规则（JWT、PEM、前缀 key、`Bearer`、URL 密码）；没有「值到哪里结束」的问题 | 稳定，不在本设计范围 |
| 名字规则 | 靠前面的名字和分隔符认值的规则（env 行、`name: value`、`--flag`、JSON 对） | 本设计的对象 |
| 值的范围 | 名字规则认定为值、要遮住的那一段 | 由十几条互相交叉的正则决定 |
| 干净收尾 | 值以允许的形式闭合，且后面是允许的边界（§4.2） | 没有这个概念：只有「读到哪算哪」 |
| 行尾遮 | 收尾不干净时，从值的起点遮到这一行结束 | 只有 `Authorization` / `Cookie` 头这样做 |
| 读法 | 同一文本的四种读：整段、实时流、存量改写、下限 | 四者各有例外 |
| 真值 | 生成一行文本时就知道哪些字符是密钥值 | 没有：生成器只放一个标记 |

不变量（实现要用机制保证的）：

- **I-R1 单调。** 任何文本，新版本遮住的字符包含上一发布版遮住的字符。（现有：v0.70.0 下限。保留。）
- **I-R2 失败方向。** 名字规则认出一个名字以后，它的值后面同一行的文本，只有在值干净收尾时才放行。
  认不准就多遮。（新增，本设计的核心。）
- **I-R3 读法一致。** 整段、任意切点的实时流、存量改写，对同一文本遮住的相同；输出再读一遍不变。
- **I-R4 名字一处定义。** 「这个名字的值要遮」在字段规则和文本规则里是同一个判断，文本规则只多带边界条件。
- **I-R5 验收有真值。** 计入「露」的字符，是生成时已知为某一对的值的字符。
- **I-R6 多遮可见。** 行尾遮照常计入 `redactedValues`，清洗报告、审批上的「已隐藏 N 个值」照常出现。

## 3. 候选边界与取舍

| | 做法 | 结论 | 理由 |
|---|---|---|---|
| A | 按来源标注：密钥进入系统时带标记，输出按标记（字面值）遮 | **不作主路径**，留作补充（§4.5） | 只对值已知的密钥有效；这些已被边界挡住（§1.2）。第三方密钥没有可标的值。而且字面值来自同一次识别，值读短了，登记的字面值一样短 |
| B | 结构化、白名单输出：给人看的只放声明过的字段，不放自由文本 | **只在已有结构处用**（现状已如此） | 工具结果与回复的自由文本就是可追溯性的产品价值。JSON 能解析时已按字段规则精确遮，那里没有值的结尾问题 |
| C | **值的结尾改成白名单：证明干净才放行，否则遮到行尾** | **采用** | 把无界的「找结尾」换成有限的「核对收尾」；新写法的失败方向从露变成多遮；规则只增不减，符合第三条底线 |
| D | 维持现状，只把新变体并进一行「类」遗留 | 不采用为终态 | 队列里还有 9 条，每条一个 R3 PR；并号只是少占编号，流入不变 |
| E | 去掉名字规则，只留形状规则 | 不采用 | 配置文件里的口令会原样显示，比现在少遮，违反「只增不减」 |

C 的本质是 B 的思路用在值的边界上：不是「认出是值的才遮」（黑名单），而是「密钥名之后，认出是干净结尾的才放」（白名单）。

## 4. 目标方案（Target Architecture）

### 4.1 四层，各管各的

| 层 | 挡什么 | 本设计动不动 |
|---|---|---|
| L0 够不着 | 平台管的密钥不进 agent 与内核进程 | 不动。只改 `secret-values.ts` 开头那段过时的理由 |
| L1 结构 | 能解析成结构的内容按字段名遮，值是什么样都遮 | 不动。阶段 2 让文本规则与它共用名字判断（I-R4） |
| L2 形状 | 值本身可认的密钥 | 不动 |
| L3 名字规则 | 自由文本里靠名字认的第三方密钥 | **改：干净收尾才放行**（§4.2） |

### 4.2 规则：干净收尾，否则行尾遮

对一行里名字规则认出的每一个「密钥名 + 分隔符」，从值的起点起核对三条：

1. **值是三种闭合形式之一。**
   - 裸值：一段不含空白、引号、反斜杠、反引号的字符。
   - 引号值：`"…"` 或 `'…'`，里面的 `\x` 作为一个整体读，到第一个没被转义的同种引号为止。
   - 转义引号值：`\"…\"`（1、3、5、7 个反斜杠），由同样长度的一串收尾，中间没有别的引号。
2. **值里没有起另一对。** 值的内容里不出现密钥名加分隔符；裸值本身不是一个密钥名或 `--flag` 的开头；
   内容不是「掩码加别的字」。
3. **值后面紧跟允许的边界。** 允许的只有：行尾；空白；`,` `;` `&` `|` `)` `]` `}` `>` `.`；反引号；全角标点；
   或者外层字符串的收尾引号（可带转义）后面再接上述之一。并且值后面 8 个空白以内不是 `:` 或 `=`（那是一个键的引号，不是值的）。

三条都满足：只遮这个值，从边界往后照常读。**任何一条不满足：从值的起点遮到行尾，写成一个 `[redacted]`。**

再加一条按格式读的：**行首的一对**（`name: value`、`NAME=value`、`export NAME=value`、`- name: value`）且是裸值时，
值按这些格式自己的定义算到行尾（或 ` #` 注释之前）。这条修的是 §1.4 的前两行，不是多遮：YAML、`.env`、INI 里行尾之前都是值。

几点说明：

- **「行」是被读的那个字符串里的一行。** 工具结果是 JSON 文本时，是解码后的字符串值里的一行（沿用遗留 916 的解码读法）。
  没被解码的文本里字面的 `\n` 不算行尾，行尾遮会一直遮到真正的换行：多遮，方向正确。
- **允许的边界是一张表，每一项是一次「这里放行」的决定。** 表里现在这些来自现有规则已经放行的地方
  （`AFTER_A_QUOTED_VALUE`、§3.220 的反引号与全角标点），所以不比现在多露。往表里加一项要说明理由并过 §8 的对比。
- **幂等是构造出来的。** 行尾遮写下的是 `name=[redacted]` 加行尾，再读时值就是一个掩码、后面是行尾，三条都满足，不变。
  遗留 950（现成的掩码后面紧贴着字）落在第 2 条上，实时读法和存量读法不再需要两套。
- **计数。** 一次行尾遮算一个值。用到计数的地方只看是否大于 0（§3.220 已核对过）。
- **线性时间。** 三条检查都是从值的起点向右的一次扫描，值里找名字只在名字可能起头的位置试，和现有规则同一种写法。

### 4.3 四种读法怎么对齐

- **整段。** 现有读法不动，在它之上加这条检查，结果取并集（§7 阶段 1）。
- **实时流。** 认出名字后扣住，直到三条有了结论：值闭合、看到边界、再看至多 8 个空白加 1 个字符。
  一旦判定行尾遮，放出一个 `[redacted]`，之后到换行为止的字符直接丢弃，不再扣留、不再重读。
  扣留超过 `STREAM_HOLD_MAX_CHARS` 还没有结论，按行尾遮处理。结论只取决于到边界为止的文本，所以任意切点与整段一致；
  对抗写法下「整词扣住、每块重读」的耗时（§3.220 的 3 倍）在行尾遮的行上消失。
- **存量改写。** 见 D3。只计数不改写的五类直接用实时读法：以前版本留下的 `TOKEN="[redacted]"<密钥>` 是「掩码后面紧贴着字」，
  实时读法现在认得，遗留 951 要的计数由此得到，不需要给这五类另配一套存量读法。
- **下限。** `withFloor` 与冻结的 v0.70.0 读法保留到阶段 3。

### 4.4 验收口径与遗留怎么登记

验收改成三条，都能在仓库里重跑：

1. **不比上一发布版多露**：沿用现有做法，各生成器乘各种子共 300 万行，逐行比遮住的字符，由遮变露 0 行。
   整段、实时流（与上一版的流在同样切点比）、存量改写各算一遍。
2. **真实格式语料上真值不露**：语料由文法生成（一组键值对的抽象表示，按 `.env`、YAML、INI、JSON、JSON 写在字符串里、
   shell 赋值与 `--flag`、PHP 与 Ruby 的 `=>`、连接串、XML 等序列化），生成时记下每个值的位置；
   断言这些位置上的字符全部被遮。每加一种格式，是一个有限的小 PR。
3. **多遮有预算**：普通文本语料（仓库自己的文本）上与上一版读得不同的行数和多遮的字符数写进 PR，超过约定比例要说明。

登记规则随之改（写进 `dev-loop.md` §4，取代第 5 条里「新的变体记进那一行」的开放式写法）：

- 上面第 1 条被打破的，是回退，照旧是发版阻塞。
- 真实格式语料上露的，登记进「类」这一行，档是「阶段内处理」，修法是给语料加格式、给名字文法加一项。
- **只在随机拼接的生成器上露、任何一种列入语料的格式都写不出来的，不登记、不单独修**：行尾遮之后这类应当只剩
  「名字没被认出来」的，它们按第二条的格式清单推进，不按写法推进。
- 只多遮的，写进「类」这一行的多遮清单，档是「挂起」，攒到有可读性投诉时一起调允许的边界表。

### 4.5 不做的，和留到以后的

- **不做按来源分档的规则**（工具输出一套、模型回复一套）。行尾遮只在异常行上触发，实测量小（§5），一套规则够用。
  出现「模型回复里正常的句子被整行遮掉」的真实反馈时再议。
- **不做会话内字面值接力**（在工具结果里认出的值，登记下来，在随后的回复里按字面值遮）。它能补上
  `the password is <密钥>` 这种句子，但要新增一份有生命周期的会话状态，短值会误伤正文。进入条件：主机上观察到这类外露。
- **不在门里按字面值遮它自己用的凭据。** 门知道自己注入的凭据的值，在结果离开门之前按字面值（含 URL 编码）遮是精确的，
  也符合「在凭据进入文本之前处理」。它是独立的一项加固，不解决本类，另行登记，由凭据席位评估。

## 9. 风险与代价

- **多遮是真实的代价，不是免费的。** 异常行从值往后整段不可见。最需要当心的是审批：执行类动作的参数里，
  如果一条命令的密钥后面收尾不干净，审批人看不到这一行剩下的部分。现状已有同样的性质（遮住的就是看不到，
  凭「已隐藏 N 个值」的二次确认放行），行尾遮把它放大到整行尾。见 D4。
- **行首格式读到行尾会多遮说明文字。** `token: used for authentication` 这样的行会从 `used` 遮到行尾
  （现在只遮 `used`；中文说明因为没有空格，现在就已经整段遮）。量在 §5：86.6 万行里 282 行。
- **允许的边界表会被不断要求放宽。** 每放一项都可能重新打开一种写法。约束：加项必须过 §8 第一行，并在表里写明理由。
- **「不登记人为构造的写法」可能被读成降低标准。** 它不降低任何已有的遮蔽（I-R1 不变），只是不再把无界的输入空间当待办。
  这一条需要维护者明确同意（D1）。
- **阶段 3 的删除有回归风险。** 所以它排在最后、以输出逐字相同为门，并且可以不做。
- **原型的数字来自我自己写的生成器**，不是两个席位用的那几个。阶段 1a 把席位的生成器入库后要重测 §5。

## 11. 本设计不解决的

- 先编码再输出的密钥（base64、逐字换行）。任何按文本认的规则都认不出，靠 L0。
- 没有名字、也没有可认形状的密钥（一个孤立的随机串、句子里的口令）。§4.5 的字面值接力能补一部分，暂不做。
- 多行值。阶段 2 评估。
- 观察类调用把第三方密钥带进 agent 上下文。这是功能所需，不在脱敏的职责里。
