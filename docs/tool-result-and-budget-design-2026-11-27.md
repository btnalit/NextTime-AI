## 0. 结论

1. **硬上限保留，计法要换。** 预算管的是失控与花费，这两件事都还在。但今天计入预算的是每次模型调用的整个上下文，
   已经缓存、只是重读的部分也全额算。一次运行的用量因此按调用次数的平方涨，一个二十步的排查即使每个工具结果都很小，
   光是起始上下文被重读二十次就接近默认预算。问题不在 200,000 这个数。
2. **把「用了多少」和「计入预算多少」分成两个量。** 前者是观察到的事实，照旧记录和显示；后者是治理对它的折算：
   新增的 token 全额计，重读缓存的按一成计。折算在每条用量记录入库时算一次并存下来，Task、目标、每日 token 预算都读它（§4.3）。
3. **Worker 要能看见自己的预算。** 设计文档 I18 写的是「80% 时经 `context` 注入警告」，实现里这条警告只到了发起调用的入口智能体，
   Worker 自己是盲的：撞线就整个 Task 失败，做过的工作没有结果。改成快到线时平台提示它收尾，带着没查完的部分正常上报（§4.2）。
4. **给模型的结果按项截断，并说实话。** 现在是在 JSON 中间按字符截断，模型不知道一共几项、看到几项，于是换着办法去补，
   越补越贵。改成只截整项、写明「前 N 项，共 M 项」和可以用来缩小范围的参数（§4.1）。
5. **谁管什么要分清。** 门决定列表回哪些字段（966）；平台扩展决定多少进上下文、并如实说明截掉了什么（本文）；
   内核照旧用门的完整回答写观察事实；预算由内核按折算后的量判定。`result_mapping` 只管写事实，不兼作给模型的视图（§3）。
6. **到线不等人，自动续作。** Worker 收尾时交出部分结果和没做完的清单；平台在链的上限之内自动起下一段，
   新的一段从干净的上下文开始，只带上一段落库的交接内容。平台按记录判断有没有进展，没有进展才停下来报给人（§4.6）。
   正常的续作不审批。
7. **预算按 Worker 定义声明。** 由所有者发布时定，受工作区上限配额约束；智能体不能给自己加预算（§4.5）。
8. **人只在两处出现**：一次性设好工作区的日成本上限，以及处理越过它或被判为失控的运行（§4.8）。
   执行类动作的审批不在本文范围，照旧。

协调线程交代要覆盖的各点，本文的处置：

| 要求 | 处置 | 在哪 |
|---|---|---|
| 旧工具结果在上下文里压缩或换成引用 | 主要由续作承担：每一段从干净的上下文开始；段内的成批折叠降为可选 | §4.4、§4.6 |
| 预算按实际新增 token 计，缓存读折算 | 采纳；用量与计入预算的量分开存 | §4.3 |
| 预算按 Worker 或任务档位声明 | 采纳，写在 WorkerDefinition 上，三档预设 | §4.5 |
| 续额全自动，无进展才停下报给所有者 | 采纳；续作是新的一段 Task，不是给原运行加额度 | §4.6 |
| 超限硬停，不超 26% | 目标是超出不过一成。超出来自用量成批上报的延迟，不只是一次在途调用；换计法后每次调用的计入量小一个量级，仍超的由 `llm-proxy` 到线即拒 | §4.7 |
| 日成本上限一次性设，平台给默认档，80% 提醒、100% 暂停 | 采纳；补上今天缺的默认值与 80% 提醒 | §4.8 |

## 1. 现状（Current Reality）

### 1.1 一个门回答走过的四层

| 层 | 现在做什么 | 上限 | 出处 |
|---|---|---|---|
| 目标系统到门 | 门读目标系统的响应 | 没有字节上限（遗留 808，开放） | 〔读〕`gatekeeper-base` |
| 门到内核 | 门把回答交给内核；docker 门的列表类每个容器带整套 `labels` | 无 | 〔读〕`gatekeepers/docker/src/transport.ts` |
| 内核自己用 | 有 `result_mapping` 的写成观察事实（用完整回答）；每次门调用另记一条 Observation | Observation 的载荷 8,000 字符，每次运行 200 条 | 〔读〕`application/gateway/observed-facts.ts`、`application/task/gate-observation.ts` |
| 内核到模型 | 平台扩展把 `{status, data, observedFactCount}` 带缩进序列化，超过上限从头按字符截断，末尾加一行「省略了 N 个字符」 | 16,000 字符，可用环境变量改 | 〔读〕`platform-extension/src/modes/gate-tools.ts` 的 `truncateToolResult` |

第四层是遗留 75 前一半的修法，worker、entry、admin 三种模式的门工具共用这一个函数。
入口与管理员模式的平台能力工具（`search`、`traverse`、`get_task` 等）不经过它，没有上限。〔读〕

### 1.2 截断的三个问题

- **截在 JSON 中间。** 模型拿到的不是合法 JSON，最后一项是半个。
- **不说项数。** 试验工作区里 `containers.list` 实有 18 个容器，Worker 看到 14 个，拒绝报总数（行为正确）。〔报〕
  图里的 Container 对象是全的，因为内核用的是完整回答；Worker 的结论却基于不全的列表。
- **留头不留尾。** `container.logs_tail` 默认取 200 行，超过上限时留下的是最旧的那部分，最新的日志被截掉。〔读〕

截断之后模型没有可走的路：不知道缺多少，也不知道哪个参数能缩小范围。
「只调一次 `compose.ls`」的那个 Task 实际报告了 11 次工具调用。〔报〕模型在用别的调用去补那份不全的列表。〔推〕

### 1.3 预算怎么计

- `recordWorkerRunUsage`（`application/task/service.ts`）对每条用量记录累加
  `inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens`，四项互不重叠（`llm-proxy/src/usage.ts` 把输入记成扣掉缓存后的净值）。〔读〕
- 判定在记账之后：到 80% 发一次 `BudgetWarning`，到 100% 把 Task 置为 `failed: budget_exhausted`、终止运行。〔读〕
- 记账本身有延迟：`llm-proxy` 把用量攒成批再报给内核，默认 2 秒冲一次（`llm-proxy/src/report.ts`）。〔读〕
  越线之后、运行被终止之前完成的调用都照样计入，所以超出的不只是一次在途调用。
  （遗留 367 讲的是另一件事：从调用方扣预算交给子 Task 之后，调用方在途那次调用晚记账。它不是这里的超出。）
- 终止还有一层延迟：Task 判失败后内核撤销 Handle，再尽力终止容器，终止失败只是吞掉；`llm-proxy` 靠撤销表认 Handle，
  默认每 15 秒同步一次。终止没成功时，模型调用最多还能再转发 15 秒。〔内核席位读〕
- 同一个四项求和今天写了三遍：`recordWorkerRunUsage` 逐条累加，以及 SQL 里的 `sumTodayTokens`、`sumTodayTokensByWorkspace`。
  其中每日 token 预算是全局环境变量 `LLM_DAILY_TOKEN_BUDGET`、按工作区求和，所有者设不了，不是配额。〔内核席位读〕
- 默认每个 Task 200,000（配额 `task.default_token_budget`，所有者可用 `set_quota` 改）；`invoke_worker` 没有预算参数；
  WorkerDefinition 上没有预算字段，只有目标计划里的 WorkerSpec 有 `tokenBudget`。〔读〕
- 花费另有一条线：每条用量按模型的费率算出 `cost_usd`（缓存读有单独的费率），工作区有日成本配额
  `task.daily_cost_budget_usd`，默认不设上限。〔读〕

### 1.4 为什么是平方

设起始上下文（系统提示词、工具定义、Skill、Worker 上下文）为 B，每次工具结果平均 r，一次运行调了 k 次模型。
第 i 次调用要把前面的全部内容再送一遍，所以累计用量约为 `k·B + r·k(k−1)/2`。

把主机上的数代进去（工具调用次数近似当作模型调用次数）：〔报〕〔推〕

| Task | 工具调用 | 用量 | 读法 |
|---|---|---|---|
| 完整容器排查 | 20 | 253,465（预算 200,000） | B 取 6,000 到 8,000 时，光 `k·B` 就是 12 万到 17 万；平均每个结果只需几百 token 就到 25 万 |
| 只查一个 compose 项目 | 11 | 超过 200,000 | 次数少而用量同样超线，说明平均每个结果大得多：反复拿到顶到上限的截断结果 |

两点读法：

- **大结果不是唯一的原因，甚至不是主要的。** 第一个 Task 里，即使每个工具结果都是零，20 次调用重读起始上下文也要用掉默认预算的六到八成。
  所以 966（门侧去掉 `labels`）必要但不够。
- **超出 26% 不是一次在途调用的量，是越线后又跑完的两三次。** 用量按平方涨，越往后的调用越大，所以不能拿平均每次一万二去除；
  超出的 5.3 万更可能是后段的两三次调用。〔推〕
  这个 Task 34 秒里调了二十来次，平均不到 2 秒一次，而用量 2 秒才报一批，再加上终止运行与撤销同步的延迟，越线后还能跑出几次（§1.3）。

本线程核实时曾按「八次顶到上限的结果」推算，与 25 万的数字也吻合，但调用次数不对。967 登记行里的那半句以本节为准。

### 1.5 I18 写的和做的差在哪

设计文档 I18：「token 到 80% 时 `llm-proxy` 上报、内核经 `context` 注入警告，到 100% 时 `llm-proxy` 返回预算耗尽错误，
Worker 本轮结束」。实现里：〔读〕

- 80% 的警告只进了**发起调用的入口智能体**的上下文（`application/linkage/budget-consumer.ts`），Worker 收不到；
- 100% 时 `llm-proxy` 的拒绝只对工作区级预算生效（`/internal/llm-budget-exhausted`），Task 级是内核事后判定加终止运行；
- Worker 被终止后 Task 没有结果。它报告过的工具调用还在（遗留 155 的记录），所以证据没丢，结论丢了。

## 2. 领域模型（只列本次涉及的）

| 概念 | 是什么 | 谁是真相源 | 本文改不改 |
|---|---|---|---|
| 门回答 | 目标系统经门给出的完整回答 | 门 | 不改；回哪些字段由门定（966 与 §5 的约定） |
| 观察事实 | 内核按 `result_mapping` 从门回答写出的事实 | 内核 | 不改 |
| 模型可见结果 | 门回答进入模型上下文的那一份 | 平台扩展 | 改：按项截断加说明（§4.1） |
| 用量 | 一次模型调用实际发生的四种 token 数 | `llm-proxy` 上报，内核记录 | 不改 |
| 计入预算的量 | 治理对用量的折算，用来和预算比 | 内核 | 新增（§4.3） |
| 预算 | 一个 Task（一段）最多可以计入多少 | 所有者：配额、WorkerDefinition、目标 | 改：多一个声明的位置（§4.5） |
| 交接 | 一段收尾时落库的内容：结论、已有发现、没做完的清单 | Worker 上报，内核存在 Task 结果里 | 新增（§4.6） |
| 续作链 | 由「接续自」关系连起来的若干段 Task，同一个委派，每一段的权限不超过上一段 | 内核 | 新增（§4.6） |
| 日成本上限 | 一个工作区一天最多花多少钱 | 所有者（配额） | 改：有默认值和 80% 提醒（§4.8） |

要守住的几条：

- **N1** 模型可见结果被截短时，模型一定被告知哪些列表不全、各看到几项共几项。不存在「不全但没说」的结果。
- **N2** 观察事实来自完整的门回答，与模型看到多少无关（现状如此，写下来防回退）。
- **N3** 用量是事实，不因治理口径改变而改写；计入预算的量由用量按一个函数算出，在每条用量记录入库时算一次并存下来，
  所有预算判定都读存下的数。以后改权重不追溯改写旧的账。
- **N4** 预算只由人的治理动作决定（配额、发布定义、确认或修订目标）。智能体的任何调用参数都不能抬高自己或下游的预算。
- **N5** 预算用尽之前，Worker 至少被提示一次还有多少余量。
- **N6** 说明行是平台的话，里面不出现门回答里的值；路径里不是普通标识符的键写成位置。
- **N7** 续作不放大权限：新的一段拿到的范围不超过上一段实际持有的，也不超过请求人此刻持有的；授权被收回链就停。
  执行类请求的保证是审批本身，续作不改变它：参数不同就是一条新请求，照样要人批。
- **N8** 续作一定有界：段数有上限，在目标里还受这一步的尝试次数、目标剩余预算与墙钟约束，整体受日成本上限约束。
  只有顶层的委派和目标的步骤由平台续作，Worker 自己起的子 Task 不续，所以界不随嵌套相乘。
- **N9** 要不要续作、有没有进展，由内核按自己记的量和记录判定。从 Worker 容器里来的任何字段都只是内容，不是依据：
  容器里的进程都能以这个 Worker 的身份上报（§4.6），所以「是不是到线了」「是不是有进展」不能由容器里的任何一方来声明。
  信任是不对称的：容器里报上来的东西只能让链提前停，不能让它多续。

## 3. 候选与取舍

| 候选 | 取舍 |
|---|---|
| 只调大默认预算 | 不解决平方增长，只是把墙往后挪；长一点的任务照样撞。可以作为换计法之前的临时手段，由所有者按工作区调配额 |
| 取消 Task 级硬上限 | 不采纳。脚本化重放或模型打转时没有东西拦；工作区日成本默认还是不设上限的 |
| 用 `result_mapping` 的映射结果当模型视图 | 不采纳。它是「写成哪些事实」的投影，按标识与新鲜度选字段；排查要看的字段是另一回事。没有映射的 Operation（`compose.ls`、`logs_tail`、检索）也就没有视图。两种投影各管各的 |
| 内核给列表结果加统一信封（`items`、`total`、`nextCursor`） | 不采纳。要改每个 Operation 的结果形状和映射路径，门实例的定义摘要跟着变，主机上要逐个确认。单次回答的项数平台扩展自己数得出；跨页的总数只有目标系统知道，原样透传 |
| 把预算单位直接换成美元 | 不采纳为主路径。没有配置费率的模型 `cost_usd` 是空的。花费这条线已经有日成本配额，继续由它管 |
| 被截掉的部分由平台扩展留着，给模型一个「取下一段」的工具 | 现在不做。每取一段都再进一次上下文；大列表的正路是在源头缩小范围。目标系统确实不能过滤的情形出现了再做（§10） |
| 运行中挂起等所有者批准续额 | 不采纳。要人逐次批，和「不靠人盯」的方向相反；还要让容器挂着等人或做会话恢复 |
| 给原运行自动加额度、让它在同一个上下文里接着跑 | 不采纳。上下文只会更长，每一步更贵；续作成新的一段正好把上下文清空 |

## 4. 目标方案（Target Architecture）

### 4.1 给模型的结果：紧凑、按项截断、说明截掉了什么（阶段 1）

改的只有 `truncateToolResult` 这一个函数和它的三个调用点，三种模式一起受益。

1. **序列化不缩进。** 嵌套结构上省两到三成字符。〔推〕不超过上限的结果除此之外逐字不变，不加任何说明行。
2. **超过上限时只截整项。**
   - 只截 `data` 里面。信封（`status`、`observedFactCount`、执行类返回的 ActionRequest 标识与状态）永远原样保留：
     模型靠 `status` 区分等待审批和被拒，截掉会让它误判。
   - 很长的字符串值留头和尾，中间换成一句「省略了 N 个字符」。日志的最新部分因此保留。尾部只留整行：内核按值前面的名字遮值，尾部从一行中间开始，就可能露出一个名字被省略掉的值；最后一段里没有行首就不留尾部。尾部里遇到开头一行被省略的私钥块，从它的 END 行之后开始（#1629 凭据席位）。
     字符串按码点切，不切在代理对中间（切坏的字符发送前会被删掉，说明行里报的字符数就对不上）。
   - 还超，就从最大的数组起从末尾去掉整项，直到放得下。每个被截的数组记下路径、留了几项、原有几项。
     「最大」按序列化后的长度比；一样长时取路径按字典序在前的；嵌在另一个数组的项里的数组各算各的，
     外层的项被去掉时里面的不再单独记。实现可以换别的规则，但必须是确定的，并写进测试。
   - 仍放不下（一个巨大的单项、极深的嵌套）才退回现在的按字符截断，说明行如实写「以下不是完整的 JSON」。
3. **说明行写三件事**：哪些路径不全、各留了几项共几项（或字符数）；不要把看到的当成全部去计数或下结论；
   这个 Operation 接受哪些参数可以用来缩小范围（取自它的 `params_schema` 的属性名），没有的话就让模型在结果里写明列表不全。
   参数名来自门的定义，不是门回答，但同样是门作者写的字符串：只保留字母、数字和下划线，最多列 8 个、每个最多 40 个字符，
   不让定义成为往模型上下文里塞话的通道。
4. **说明行有界。** 被截的路径最多列 5 条，其余只给条数；整个说明行不超过 600 个字符。

要守住的性质（验收按这些写测试，不规定实现）：

- 输出不超过上限加说明行的上限（600 个字符）；信封字段逐字不变；
- 除最后那种退路外，正文能被解析成 JSON；每个留下的数组是原数组的前缀；说明行里的数字准确；
- 同样的输入得到同样的输出；留下的字符串里没有孤立的代理字符；
- 说明行不含门回答里的值（N6）。

上限的数值 16,000 字符先不动。不缩进之后同样的上限能装下更多内容。

三种模式共用这一个函数，都跟着变。入口和管理员模式的工具结果人在控制台的工具详情里也看得到，
不缩进会改变那里的显示，所以阶段 1 的 PR 要 UX 席位看一眼。

### 4.2 软着陆：Worker 在到线前被提示收尾（阶段 1）

- 平台扩展在每次模型调用前要知道两个数：这个 Task 的预算和已经计入的量。预算从 `get_task` 读（它已经带 `tokenBudget`，
  Worker 的 Handle 本来就持有这个能力）。
- **已计入的量在扩展里本地累加。** pi 席位对照 pi 1.1.0 的源码核对过：每条助手消息的用量带输入、输出、缓存读、缓存写四种数，
  输入是不含缓存的净值，口径与 `llm-proxy` 一致。〔pi 席位读〕要做对三件事：
  1. **压缩调用也要算。** Worker 的运行时设置没有关掉 pi 的自动压缩，所以它默认是开的；压缩那一次模型调用经过 `llm-proxy`、
     计入内核，但扩展只能从压缩事件里读到它的用量，而且可能读不到。读不到时按保守方向估（例如按压缩前的上下文大小全额计）。
  2. **起点不是 0。** 同一个 Task 重跑时用量是跨运行累计的。扩展启动时读一次 `get_task`（现在本来就读），
     把内核的数当起点，再往上加。
  3. **折算和内核用同一份。** 折算函数放进 `packages/shared`，权重 w 由 `get_task` 随预算一起给出。
     这样扩展的估计是 N3 说的同一个函数的第四个调用方，不是第四种口径；内核和运行时镜像版本不一致时也不会算错。
     阶段 1 上线时内核还没有 w，扩展按全额估，和内核当时的判定一致。
  做到这三件，每次模型调用前不需要再读内核。读 `get_task` 的已计入量只留作本地累加出错时的兜底，读不到就不提示，不影响运行。
- **提示的时机按上一次调用的大小预测，不按固定百分比。** 当「剩余量小于上一次调用计入量的若干倍」时提示
  （先取 3 倍，实现时按实测调）。
  理由：越到后面每一步越贵，而且上报这一步自己也要再读一遍全部上下文；按固定的 80% 提示，在长运行里常常只剩一两步的余量。
- **提示作为末尾一条短消息加进去，并且把缓存断点留在历史上。** worker 模式今天没有装断点搬移（Worker 上下文放在最前面，
  以前用不着）。不搬的话断点会落在提示上，下一次请求整段对话按写入价重写一次，而这正发生在余量最紧的时候，
  按 §4.3 缓存写入是全额计的，提示自己就可能把运行推过线。做法是现成的：入口模式的现场上下文用的
  `keepCacheBreakpointOnHistory`（`prompt-cache.ts`），worker 模式追加提示时同样调用它。〔读〕
- **提示一旦出现，之后每次的文字保持不变**：只写「余量不多了」这一档，不写精确的数字，否则断点前的内容每次都不同。
  内容是：余量不多了，现在就用手上的结论调用 `report_result`，把没查到的写进 `findings`。
- 内核 100% 的硬停照旧，是兜底。80% 给入口智能体的那条警告照旧。

效果是会撞线的运行变成「完成，带着没做完的清单」，不再是失败且没有结果。阶段 1 先把没做完的写进 `findings`；
机器可读的交接字段随续作一起加（§4.6）。

### 4.3 计法：用量与计入预算的量分开（阶段 2）

定义一个折算函数，放在 `packages/shared`，所有要算这个量的地方都调它：

```
计入预算的量 = 输入（净值） + 输出 + 缓存写入 + 缓存重读 × w        w 默认 0.1（V1）
```

- **每条用量记录入库时算一次，存成 `llm_usage` 上的一列**，逐条向上取整。Task 上另有一列是它的累计。
  今天写了三遍的求和（§1.3）都改成读这一列。这样取整只定一次；以后改 w 只影响之后的记录，不改写旧的账（N3）。
- `tasks.tokens_used` 保持原义（四项全额相加），控制台照旧显示。预算判定、80% 警告改用计入量。
- **读 `tokens_used` 的地方不止一处，阶段 2 要逐个定用哪一列。** 内核席位读到的至少有：目标的用量汇总（含规划器的 token）、
  给在途 Task 预留的余量、从调用方给子 Task 分预算、目标预算用尽的扫描、目标不变量巡检、给规划器的「中位用量」提示。
  默认做法：凡是和预算比的都用计入量；巡检跟着改，否则会把正常的目标报成超预算；给规划器的提示也用计入量，
  因为它是用来估这一步该给多少预算的。
- 调这个函数的还有两处，不许另写：平台扩展的本地累加（§4.2）和 `llm-proxy` 的到线即拒（§4.7）。
  阶段 2 之后软着陆从 `get_task` 读的是计入量，不再是 `tokensUsed`，否则提示会早很多。
- 线上契约里 Task 多一个字段。控制台把两个数都显示出来，并写明其中多少是重读，否则所有者会看到
  「用了 25 万、预算 20 万、却没有停」而不明白。
- 升级时已有的行把新列回填成四项全额之和（偏保守，在途的 Task 不会突然多出余量）。
- **已确认、还在跑的目标，预算数是按旧计法确认的**，升级后同样的数大约能花到原来的三倍。默认接受这一点并写进发版说明：
  目标另有墙钟和日成本上限管着，为它给每个目标记下确认时的计法不值得。协调线程可改。
- 不提供缓存的模型没有重读这一项，计入量等于用量，和今天一样。这是对的：那种情况下每一步确实都要重新付全价，
  对它们起作用的是 §4.4 的折叠和 §4.5 的档位。

按这个计法重算 §1.4 的第一个 Task：新增部分约 2 到 3 万，重读约 22 万折成 2.2 万，合计约 5 万，是默认预算的四分之一。〔推〕
同样的 200,000 大约能做三倍多的工作，而一个打转的 Worker 仍然会被停住。

这一步放宽了「同一个预算数能花多少钱」。真正管钱的应当是工作区日成本配额，它默认不设上限（V3）。

前提要核对一件事：主机上这类 Task 的用量记录里缓存重读是不是非零。是，本节按上面生效；不是，说明缓存没命中，
要先查缓存为什么没命中（Worker 上下文已经按可缓存的位置放了，`modes/worker.ts` 的 `withWorkerContextFirst`）。

### 4.4 段内的旧工具结果折叠（可选，有数据再做）

- 做法：平台扩展在组装上下文时，把较早的工具结果换成一行占位（哪个工具、原来多少字符、需要的话再调一次），最近的几个不动。
- 必须成批做：改动历史中间的内容会让它后面的缓存全部失效、按写入重算一次。规则只由历史决定，折过的不再变。
- 它的收益被另外两件事分走了大半：换计法之后重读只按一成计（§4.3）；续作让每一段从干净的上下文开始，
  而且交接内容是落库的、可追溯的（§4.6），比留在对话里的摘要可靠。所以它降为可选：
  阶段 2、3 上线后如果单段之内仍然撞模型的上下文窗口，或者在不提供缓存的模型上花费明显，再做。
- 折叠掉的内容并没有丢：门调用的 Observation 和 Worker 报告的工具调用记录都在内核里。
- **pi 自带的自动压缩今天就在做一种段内折叠**（§4.2）：上下文接近模型窗口时，它用一次额外的模型调用把较早的历史总结掉，
  代价是那一次调用加上缓存失效。它留着，防的是撑爆上下文窗口；它的用量按 §4.2 计入本地累加。
  续作上线、有了数据之后再定要不要对 Worker 关掉按阈值的压缩、只留溢出时的恢复。这是 pi 席位的倾向，本文照此。

### 4.5 预算在哪声明、谁能改（阶段 4）

- WorkerDefinition 的内容多一个可选的 `tokenBudget`，与目标计划 WorkerSpec 里已有的同名字段同一个意思。
  定义由人发布，所以这是一次治理动作；智能体只能提议定义，不能发布。
- 新配额 `task.max_token_budget`：工作区里任何定义、任何一步能声明的上限。
- 一个 Task（一段）的预算取：定义声明的值，没有就用 `task.default_token_budget`；不超过 `task.max_token_budget`；
  在目标里再不超过目标剩余的量（现有逻辑）。`invoke_worker` 仍然没有预算参数（N4）。
- 控制台发布定义时给三档预设加自定义，不让人手打一个裸数。数值是产品默认，建议 200,000、600,000、2,000,000，
  上限配额默认等于最高一档。内置包的 Worker 文件可以带这个字段，安装审阅时显示。
- **跨多步的长任务的位置是目标。** 目标有整体预算和墙钟，每一步是有界的 Task；目标的预算用尽时进入
  `paused(budget_exhausted)`，请求人用 `revise_goal` 改预算、`resume_goal` 恢复。〔读〕
  这是整件事的总上限，是人该出现的地方；一步之内的续作不到这一层（§4.6）。

### 4.6 到线之后：自动续作（阶段 3）

**续作是什么。** 一段 Task 按 §4.2 收尾并完成，结果里带着交接；平台随后起一个新的 Task 接着做。
新的一段是全新的运行和全新的上下文，输入是原来的任务加上一段的交接。它不是给原运行加额度。
这样做同时解决两件事：不用人批，以及上下文被清空，平方增长从头算起。

**交接里有什么。** 结果契约加一个可选字段，由模型填「还没做完的事项」。它是下一段的输入，不是续作的依据。

**哪些 Task 由平台续作。** 只有两种：入口智能体或人直接发起的顶层委派，和目标的步骤。
Worker 自己用 `invoke_worker` 起的子 Task 不由平台续作：它的部分结果和未完成清单回到调用它的 Worker，
由那个 Worker 在自己的预算和嵌套上限之内决定要不要再委派；子 Task 不经过下面的「待判」，完成后直接交回调用方。理由有两条。平台代为续作是因为顶层的调用方要等到人下一次发言才看到结果，
而调用子 Task 的 Worker 是正在运行的智能体，不存在等人的问题。其次，子 Task 的预算来源各不相同（在目标里从目标余量和调用方未用的部分里分，
目标外每个子 Task 拿一份默认预算、不从调用方扣〔内核席位读〕），由平台续作会让段数的界随嵌套相乘（N8）。

**「到线」由内核判，不由容器里的任何一方声明（N9）。** 第二稿写的是平台扩展在上报里带一个模型碰不到的标记；
两个席位都指出这挡不住：默认的 Worker 有 `bash`，内核按容器地址认 Handle，容器里任何进程都能直接调上报的能力并带上任何字段。
改成内核用自己记的数判断：

- **判据。** 这个 Task 剩余的可计入量小于本段预算的 30%，就算接近线；这是主条件，它和每次调用的大小无关。
  补充条件：剩余小于这次运行最近三次调用里最大的那一次计入量的 6 倍。用量记录带会话标识，能对到 Task，〔读〕
  取最近几次里最大的而不取最后一条，是因为已到的最后一条可能是较早、较小的一次。数值在实现时用夹具定。
- **什么时候判。** 受理上报、把 Task 置为完成的那个事务里，只记下「带交接，待判」。判定经出站事件延后一个间隔再做
  （先取 10 秒，大于 `llm-proxy` 的 2 秒一批加一次失败重试），那时最后几次调用的用量已经落定。
  Task 已结束之后到达的用量照样累加，〔内核席位读〕所以越晚判，剩余只会越少：出错只会偏向「没续上」，那一侧是有界的。
- **判定是一个领域事件，只发生一次。** 判的时候锁 Task 行（和分子预算、记用量同一把锁），把用到的数和结论一起落库：
  预算、计入量、最近调用的计入量、门槛、续或不续及原因。之后任何地方要知道结论都读这条记录，不重新算。
- **要守住的性质**：扩展发过提示之后的上报，内核一定判为接近线。在落定的数上它能证明：扩展在剩余小于上一次调用计入量的 3 倍时提示，
  正常收尾时那一次调用就在内核看到的最近三次之内，而提示之后剩余只会更少。模型无视提示继续跑的话，剩余很快落到 30% 的主条件之内。
  测试按这个写，并覆盖用量晚到一批、提示之后发生过一次压缩这两种情形。
- 接近线，并且上报里有未完成清单，才算「到线、没做完」，才续。扩展只负责发提示，不承担任何判定。
- 要伪造这个条件，就得真的把预算花到接近线；而花掉的量本来就在界内，后面还有段数上限、无进展判定和日成本上限。
- 判偏了的后果是有界的：判严了，一次诚实的收尾没有被续上，结果照常交付并写明还剩什么，和不开续作时一样；
  判松了，一个早早放弃并列了清单的 Worker 多得到一段，仍在段数上限之内。

Worker 自己判断做不下去的其它情形（没到线）不触发续作。

**谁来起下一段，新的一段拿到什么权限（N7）。** 两条路的准入不一样，不能混用。

- **目标里的步骤**：推进器把续作当作这一步的下一次尝试，走步骤今天的准入（以请求人此刻的入口范围为父，
  因为计划是人确认过的）。〔读〕要写明的三件事：
  1. 推进器判一次完成的尝试时先看交接：结论还是「待判」就等下一拍；判为续作就起下一次尝试，不进入这一步的验收。
     今天带着结果完成的尝试会被直接判成成功，〔内核席位读〕不改这一点，部分结果就会被当成这一步的产出。
  2. 步骤声明了输出 schema 时，带交接的上报可以不带 `output`，受理时不因此拒绝；判定的结论是不续时，没有合格输出的尝试按 `no_result` 处理。
     只有链的最后一段的结果过输出 schema 和这一步的验收。今天只有失败的尝试才会走到 `no_result` 的返工，完成的尝试直接判成功，
     〔内核席位读〕所以推进器要把「已完成、带交接、不续、没有合格输出」显式判成违反输出约定，和其它没有结果的尝试一起计数，并钉一个用例。
  3. 续作占用这一步的尝试次数，和瞬时失败的重试共用同一个计数。尝试上限是 2 的步骤只能续一次。
  今天 `budget_exhausted` 的尝试会让整个目标暂停等人；改后，带着交接完成的尝试直接续作，目标不暂停。
- **目标之外的顶层委派**：内核在判定事件之后起下一段（同一类出站事件消费者已经在用）。入口智能体不参与：
  它只在用户下一次发言时才看到 Task 的结果，〔读〕等它就是等人。准入**不能**照搬步骤的做法：
  顶层委派的父是调用方自己的 Handle，可能比请求人的入口范围窄（调用时用 `gates` 收窄过；父没有的非执行类门或能力被静默去掉）。
  〔内核席位读〕拿请求人的入口范围去铸第二段，第二段会比第一段宽，这碰到「隔离只增不减」的底线。所以：
  1. 新的一段的父范围 = **上一段 Handle 的范围 ∩ 请求人此刻的入口范围**。上一段的范围要随 Task 落库，Handle 撤销之后照样读得到。
  2. 其余检查照搬步骤尝试的那一组：请求人是否被停用、角色能否起 Worker、评测封存、Task 配额。
  3. 并发配额不够时等：按出站事件现有的退避重试，到上限（先取 10 分钟）仍不够就结束这条链，结果照常交付，写明原因。
  4. 签发依据（遗留 702）加一种：「续作自某 Task」。审计上要能看出这个 Handle 不是任何人或智能体当场要的。
  5. 出站事件至少投递一次，所以「接续自」加唯一约束：一个 Task 最多有一个后继，同一个事件重放不会起出两段。

**什么时候不续（内核判定，N8、N9）。**

| 条件 | 判定依据 | 之后 |
|---|---|---|
| 段数到上限 | 新配额 `task.max_continuations`，默认 3（共四段），设成 0 即关闭续作；目标的步骤再受尝试次数约束 | 链结束，最后一段的结果照常交付，写明还剩什么 |
| 目标预算或墙钟用尽 | 现有逻辑 | 目标 `paused(budget_exhausted)`，等请求人 |
| 日成本到上限 | §4.8 | 不再起新的一段，等所有者或等次日 |
| 没有进展 | 见下 | 链结束，标成需要人看，通知请求人与所有者 |
| 准入不过 | 请求人被停用、权限被收回、交集为空、配额一直不够 | 链结束，说明原因 |
| 硬停（没来得及上报） | Task 是 `failed: budget_exhausted`，没有交接 | 不续，和今天一样；软着陆就是为了让这种情况变少 |

**「没有进展」怎么判。** 主判据只用内核自己记的两样东西：

- 这一段经门做过的调用：审计里 `observe_operation`、`request_action` 的行，按 Operation 加参数摘要比
  （摘要用执行类请求去重现成的规范化 JSON 再取哈希）；
- 这一段新写出、链里以前没有的观察事实。

两样都没有新的，就判为没有进展。每次门调用另记的 Observation 每次运行有 200 条上限，长运行上会漏，不拿它当主判据。〔内核席位读〕

容器里报上来的（未完成清单、遗留 155 的工具调用记录）只用来提前停：清单与上一段完全相同就停。它们不能用来证明有进展（N9）。

盲区要说清楚：容器里的 shell 命令做了什么，内核看不见。只在 shell 里干活、不经门的 Worker，主判据上永远是「没有新的门调用」，
第一次续作总会发生（那时没有上一段可比），第二段之后就停。这是偏严的方向，符合「宁可早停一段，也不让一个打转的 Worker 把四段都跑完」。
这类 Worker 多起来之后需要别的信号，见 §10。规则的其余细节在实现时用夹具定。

**执行类请求。** 新的一段的上下文里列出这条链已经发起的 ActionRequest 及其状态。去重直接复用目标里现成的那套规则
（GO3c），把身份里的「步骤」换成「链的第一段 Task」，不另写一套：只有最新一条还在途、已执行、已核实，
或结果未知且没人决定重跑时才回放已有的那条；被拒、过期、撤回的，新建一条并重新走审批；结果未知时拒绝再发，重跑要留痕的决定。〔内核席位读〕
在目标里，续作本来就是这一步的又一次尝试，这套规则已经覆盖。去重只是方便，保证是审批本身：参数稍有不同就是一条新请求，照样要人批（N7）。

**能看见。** Task 上记「接续自哪个 Task」；控制台把一条链显示成一个任务的几段，最后一段的结论在最上面，
每段的用量、计入量、为什么续或为什么停（读判定事件）都能看到。请求人看到的是一个结果，不是四张卡片。

### 4.7 硬停超出多少

超出的量是越线之后、运行被终止之前完成的所有调用：在途的那一次，加上用量还没报到内核的那一批（默认 2 秒），
再加上终止运行本身的延迟；终止容器没成功时，还要加上 `llm-proxy` 同步撤销表的间隔（默认 15 秒，§1.3）。调用越快、每次越贵，超得越多；§1.4 的例子里是预算的四分之一。目标定为「超出不超过一成」。

- 换计法（§4.3）之后，每次调用的计入量是它新增的部分加一成的重读，同一个例子里一次只占预算的百分之一二，
  越线后多跑两三次也在一成以内。〔推〕软着陆（§4.2）让多数运行根本到不了线。
- 仍然超的（不提供缓存的模型、很快的模型），在第一手记账的地方拦：`llm-proxy` 是每次调用最先知道用量的一方，
  让它知道这个会话的预算，自己累加，到线就不再转发、返回预算耗尽；平台扩展收到后用已有的兜底上报收尾。
  这正是 I18 原文「到 100% 时 `llm-proxy` 返回预算耗尽错误」，现在只在工作区级做了。内核的事后判定留作兜底
  （`llm-proxy` 重启会丢内存里的累计）。它怎么得知预算（随 Handle 带出，或会话第一次调用时向内核问一次）由实现定。
  列为阶段 6，阶段 2 之后实测仍超一成再做。做的时候把撤销也算进去：到线即拒之后，这个会话在 `llm-proxy` 里就地作废，
  不等下一次撤销同步。累加用 `packages/shared` 里的同一个折算函数（§4.3）。

### 4.8 日成本上限：人该出现的唯一常规位置（阶段 5）

现状：`task.daily_cost_budget_usd` 默认不设上限；设了之后，到线时新的委派被拒，`llm-proxy` 对这个工作区的所有模型调用返回预算耗尽，
到下一个 UTC 零点恢复。工作区级的 80% 提醒在代码里还没有任何地方发出。〔读〕

改成：

- **有默认值。** 新建工作区时带一个默认档，所有者可以在创建时或之后改。三档预设的数值是产品默认，建议每天 5、20、100 美元，
  默认取中间一档。已有的工作区不自动改，控制台给所有者一条提示，设一次就消失。
- **80% 提醒所有者**，到线时的行为不变。到线后链不再续、目标按现有逻辑暂停；所有者调高上限或等次日，其余自动恢复。
- **管不到的要说出来。** 花费是按模型的费率算的，没有配置费率的模型花费记为空，这条上限对它不起作用。
  模型页和工作区的预算设置里要明说哪些模型处于这种状态。那种情况下起作用的只有 token 预算和段数上限。

换计法、自动续作之后，人和预算打交道的地方：

| 情形 | 今天 | 改后 |
|---|---|---|
| 正常但步数多的任务 | 失败，没有结果，人重新发起 | 自动分段跑完 |
| 快到单段预算 | Worker 不知道 | 平台提示，Worker 收尾交接 |
| Worker 打转 | 跑到预算硬停 | 无进展即停，通知人 |
| 一天花多少钱 | 默认没有上限 | 有默认上限；80% 提醒；到线暂停，等所有者或次日 |
| 执行类动作 | 逐次审批 | 不变 |

## 5. 和 966、968 对齐的口径

**966（门侧投影）与本文的分工**

- 966 只改门：列表类 Operation 回摘要字段，大块的附属结构只在单项读取里回。它不动 `platform-extension`；
  「给模型的 JSON 不缩进」放在本文阶段 1，这样 966 是一个只涉及门的 PR。
- 由 966 立下、以后每个内置门照做的约定：
  1. 列表类默认回摘要：标识加排查用得到的状态字段；
  2. 目标系统支持时提供缩小范围的参数（按状态、按名字、分页），并在 Operation 描述里写出来；
  3. 每个内置门带一个「载荷预算」测试：用一份有代表性的夹具（docker 门建议 40 个容器、带真实长度的名字与镜像名），
     断言列表类结果序列化后不触发截断。门槛由 966 的作者按实测定，写进测试。
- docker 门要加过滤参数（例如按状态）会改 `params_schema`，门实例的定义随之变化，主机上要确认一次。
  不单独为它开主机步骤，和下一次 docker 清单的改动合在一起。

**968（本体词汇进 Worker 上下文）要守的预算**

词汇放在 Worker 上下文里，是每次调用都要重读的固定部分，直接加在 §1.4 的 B 上。所以：

- 词汇段有上限，建议 4,000 字符；
- 先放与这个 Worker 相关的：它能调用的 Operation 的 `reads` / `writes` 里出现的对象类型，以及两端都在其中的 LinkType 签名；
  放不下的其余部分只列名字，再放不下就只给个数；
- 一行一个 LinkType 签名、一行一个对象类型与它的标识键，不放属性的完整定义。

同一段里的「相关事实」（`search` 默认最多 50 条，逐条序列化）今天没有上限，随 968 一起给一个。〔读〕

## 7. 验证

- **阶段 1**：截断函数按 §4.1 的性质写属性测试；worker 模式的 SDK 测试里放一个 18 项的列表，断言模型看到的是合法 JSON 加
  「共 18 项」；`logs_tail` 超长时留下的是尾部；说明行不含夹具里的任何值。软着陆用脚本化模型跑一个预算很小的 Task，
  断言结果是 `completed` 且 `findings` 里有未完成的说明，而不是 `budget_exhausted`。
  提示出现的那一次和它之后的一次模型调用，缓存重读不归零（断点留在历史上）；一次压缩之后本地累加的数不小于内核记的数；
  信封字段在截断前后逐字相同。
- **阶段 2**：同一组用量记录，Task 的累计、目标的汇总、每日 token 预算读到的计入量一致，并且等于扩展和 `shared` 函数逐条算出的和；
  没有缓存重读的记录，计入量等于用量；回填后在途 Task 的判定不变；改 w 之后旧记录的计入量不变；目标不变量巡检不把正常的目标报成超预算。
- **阶段 3**：脚本化模型跑一条链，断言：第二段的上下文里没有第一段的工具结果、有它的交接；段数到上限即止；
  两段的未完成清单相同时在第二段后停下并标成需要人看；同一个执行类请求在第二段再发时返回第一段的那个；
  请求人的授权在两段之间被收回时链停下；离线还远时直接调上报的能力并带上未完成清单，不触发续作；
  扩展发过提示之后的上报，在用量晚到一批的情况下仍被内核判为接近线；判定事件只有一条，重放出站事件不会起出两段。
  权限：第一段用 `gates` 收窄过时，第二段拿不到被收掉的门；第一段的父没有 `invoke_worker` 时第二段也没有；
  Worker 起的子 Task 带交接完成时平台不续。进展：两段的门调用和新观察事实都没有新增时停下，即使上报的清单和工具调用记录每段都不同；
  被拒或过期的执行类请求在下一段重发时是一条新请求，重新走审批。目标里：带交接完成的尝试不让目标暂停、不进入这一步的验收，占用一次尝试；目标预算用尽时照旧暂停。
- **阶段 5**：没有设上限的已有工作区行为不变；新工作区带默认档；80% 时所有者收到一次提醒；没有费率的模型在设置页被点名。
- **真实模型一轮**：阶段 0 和 1 合入后，在 staging 用真实模型把「完整容器排查」跑一次，记下工具调用次数、用量、
  缓存重读占比、是否完成。计入付费额度，量级是一个 Task。阶段 2 之后同一任务再跑一次，核对 §4.3 的估算。
- **主机**：升级后在试验工作区重跑清单里的三个任务，结果进主机升级报告。

## 8. 风险与代价

- **放宽了单个 Task 能花的钱。** 同一个预算数在新计法下能跑更久。对策是 V3 的日成本上限。三档是产品默认；主机上实际设的数只记在私有文档里。
- **两个数并存会让人困惑。** 控制台必须同时给出用量和计入量并说明差别，否则是新的「看不懂」。
- **软着陆依赖模型听话。** 模型可以无视提示继续调用工具；那时硬停仍然兜底，结果和今天一样。
- **自动续作会多花钱。** 一个原来在 20 万处失败的任务，现在最多可以跑四段。这是有意的：它换来的是任务做完。
  上面有三层界：段数、目标预算、日成本上限；日成本没设上限的工作区只有前两层，所以阶段 5 的默认档要在阶段 3 之前或同时上。
- **内核的「到线」门槛会判偏。** 判严了，诚实的收尾续不上，退回到「交付部分结果」；判松了，多给一段。两头都有界（§4.6）。
  门槛比提示宽这一条写成测试，不靠两处各自调参时记得对齐。
- **「没有进展」会误判。** 判严了，正常的长任务被提前停（不经门、只在 shell 里干活的 Worker 一定会，§4.6）；判松了，打转的 Worker 多跑几段。先取偏严的规则，
  被停下的链在控制台能看到原因，由人继续；误判的样本进夹具。
- **交接写得差，下一段就做不好。** 新的一段只知道交接里写的。提示词要求把已确认的事实和没做的事项分开写；
  真实模型一轮里专门看第二段有没有重做第一段的事。
- **段内折叠可能折掉模型还要用的内容。** 所以它是可选项，门槛宁可保守。
- **按项截断改变了模型看到的文本形状。** 脚本化的验收里有断言工具结果原文的，要一起改。
- **w 是一个产品常量，不是事实。** 不同模型的缓存读费率不同。取一个固定值是为了让预算数字可解释；
  要精确到钱，看的是 `cost_usd`。

## 9. 已定的默认与留给维护者的事

协调线程 2026-11-27 按维护者的方向定下三项默认，维护者可撤回：

| | 问题 | 默认 |
|---|---|---|
| V1 | 预算怎么计 | 按计入预算的量判定：新增的全额，缓存重读按一成（w = 0.1）；默认每段 200,000 不变 |
| V2 | 到线之后 | 全自动续作，不审批；段数上限默认 3 次续作；无进展、越过目标预算或日成本上限才停下来找人 |
| V3 | 日成本上限 | 所有者一次性设；平台给三档默认，新工作区取中间一档；80% 提醒，到线暂停等所有者或次日 |

留给维护者的只有一件一次性的事：阶段 3 上主机之前，在控制台给主机上现有的工作区各选一档日成本上限
（已有工作区不会被自动改）。数值只记在私有文档里。

想改的话可以改的旋钮：w、段数上限、三档的数值、`tokenBudget` 的三档数值。它们都是配额或产品默认，改起来不动结构。

其余由协调线程按本文的默认做法定：按项截断与说明行的写法；上限 16,000 字符不变；软着陆的预测规则；
内核判「到线」的门槛与延后的间隔；Worker 的自动压缩设置；Worker 起的子 Task 不由平台续作；
已确认、在跑的目标按新计法继续（写进发版说明）；带交接的上报可以不带 `output`；
「没有进展」的判定规则；门的列表约定与载荷预算测试；968 词汇段的上限与排序。

## 10. 本设计不解决的

- 门读目标系统响应的字节上限（遗留 808）。它在本文四层的最上游，仍然需要。
- 入口、管理员、交互模式里平台能力工具的结果没有上限（§1.1）。入口会话没有 Task 级预算，行为改动要过 UX，另行处理。
- 被截掉的部分的本地续取（§3）。
- 上报被拒后给 Worker 一次改正机会（968 里已写明暂不做）。
