# 工具结果进上下文的量与 Task 预算的计法（设计决定，遗留 967）

> 状态：默认方案第一稿，待「pi 运行时」「内核」两个席位独立评审。§9 的 V1–V3 待维护者拍板，每项有不回复时的默认做法。
> 本文只出设计，不改运行时代码。
> 起因：遗留 966、967、968（2026-11-27 登记）。v0.70.1 主机的试验工作区里，内置包 ops-base 的 Worker 做一次常规容器排查
> 就 `budget_exhausted`；维护者随后在控制台读到这两个 Task 分别报告了 20 次和 11 次工具调用，并问：预算是不是定得太死、
> 长任务怎么办、硬上限还有没有必要、有没有能自动解决的做法。
> 上位文档：`graph-ai-middle-platform-design.md` §5.4 I18（失控防护）、§7.4（平台扩展的三种模式）。
> 标注：〔读〕读代码或文档得出；〔报〕主机上实测后转述给本线程的（管理员智能体的清单、维护者在控制台读到的数）；〔推〕推断，未核对。

## 0. 结论

1. **硬上限保留，计法要换。** 预算管的是失控与花费，这两件事都还在。但今天计入预算的是每次模型调用的整个上下文，
   已经缓存、只是重读的部分也全额算。一次运行的用量因此按调用次数的平方涨，一个二十步的排查即使每个工具结果都很小，
   光是起始上下文被重读二十次就接近默认预算。问题不在 200,000 这个数。
2. **把「用了多少」和「计入预算多少」分成两个量。** 前者是观察到的事实，照旧记录和显示；后者是治理对它的折算：
   新增的 token 全额计，重读缓存的按一成计。Task、目标、工作区每日三处预算用同一个折算函数（§4.3）。
3. **Worker 要能看见自己的预算。** 设计文档 I18 写的是「80% 时经 `context` 注入警告」，实现里这条警告只到了发起调用的入口智能体，
   Worker 自己是盲的：撞线就整个 Task 失败，做过的工作没有结果。改成快到线时平台提示它收尾，带着没查完的部分正常上报（§4.2）。
4. **给模型的结果按项截断，并说实话。** 现在是在 JSON 中间按字符截断，模型不知道一共几项、看到几项，于是换着办法去补，
   越补越贵。改成只截整项、写明「前 N 项，共 M 项」和可以用来缩小范围的参数（§4.1）。
5. **谁管什么要分清。** 门决定列表回哪些字段（966）；平台扩展决定多少进上下文、并如实说明截掉了什么（本文）；
   内核照旧用门的完整回答写观察事实；预算由内核按折算后的量判定。`result_mapping` 只管写事实，不兼作给模型的视图（§3）。
6. **预算按 Worker 定义声明。** 由所有者发布时定，受工作区上限配额约束；智能体不能给自己加预算。
   长任务走目标（GoalRun）：每一步是有界的 Task，整体预算在目标上，用完是暂停等人改预算再恢复，这一层平台已经有了（§4.5）。
7. **不建议先做「运行中申请续额、等人批」。** 它要让容器挂着等人，或者做会话恢复。更省的做法是到线时交出部分结果，
   由人或入口智能体说继续，再起一个续作 Task（§4.6，V2）。

协调线程交代要覆盖的五点，本文的处置：

| 要求 | 处置 | 在哪 |
|---|---|---|
| 旧工具结果在上下文里压缩或换成引用 | 采纳，成批折叠；排在换计法之后，因为两者部分互相替代 | §4.4 |
| 预算按实际新增 token 计，缓存读另计或折算 | 采纳，折算；用量与计入预算的量分开存 | §4.3 |
| 预算按 Worker 或任务档位声明 | 采纳，写在 WorkerDefinition 上，三档预设 | §4.5 |
| 接近上限时申请续额，走所有者审批 | 改成「软着陆加续作 Task」为默认；运行中挂起列为备选，不建议 | §4.6 |
| 超限硬停，不超 26% | 目标是超出不过一成。超出来自用量成批上报的延迟，不只是一次在途调用；换计法后每次调用的计入量小一个量级，仍超的由 `llm-proxy` 到线即拒 | §4.7 |

## 1. 现状（Current Reality）

### 1.1 一个门回答走过的四层

| 层 | 现在做什么 | 上限 | 出处 |
|---|---|---|---|
| 目标系统到门 | 门读目标系统的响应 | 没有字节上限（遗留 808，开放） | 〔读〕`gatekeeper-base` |
| 门到内核 | 门把回答交给内核；docker 门的列表类每个容器带整套 `labels` | 无 | 〔读〕`gatekeepers/docker/src/transport.ts` |
| 内核自己用 | 有 `result_mapping` 的写成观察事实（用完整回答）；每次门调用另记一条 Observation | Observation 的载荷 8,000 字符，每次运行 200 条 | 〔读〕`application/gateway/observed-facts.ts`、`application/task/gate-observation.ts` |
| 内核到模型 | 平台扩展把 `{status, data, observedFactCount}` 带缩进序列化，超过上限从头按字符截断，末尾加一行「省略了 N 个字符」 | 16,000 字符，可用环境变量改 | 〔读〕`platform-extension/src/modes/gate-tools.ts` 的 `truncateToolResult` |

第四层是遗留 75 前一半的修法，worker、entry、admin 三种模式的门工具共用这一个函数。
入口与管理员模式的平台能力工具（`search`、`traverse`、`get_task` 等）不经过它，没有上限。〔读〕

### 1.2 截断的三个问题

- **截在 JSON 中间。** 模型拿到的不是合法 JSON，最后一项是半个。
- **不说项数。** 试验工作区里 `containers.list` 实有 18 个容器，Worker 看到 14 个，拒绝报总数（行为正确）。〔报〕
  图里的 Container 对象是全的，因为内核用的是完整回答；Worker 的结论却基于不全的列表。
- **留头不留尾。** `container.logs_tail` 默认取 200 行，超过上限时留下的是最旧的那部分，最新的日志被截掉。〔读〕

截断之后模型没有可走的路：不知道缺多少，也不知道哪个参数能缩小范围。
「只调一次 `compose.ls`」的那个 Task 实际报告了 11 次工具调用。〔报〕模型在用别的调用去补那份不全的列表。〔推〕

### 1.3 预算怎么计

- `recordWorkerRunUsage`（`application/task/service.ts`）对每条用量记录累加
  `inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens`，四项互不重叠（`llm-proxy/src/usage.ts` 把输入记成扣掉缓存后的净值）。〔读〕
- 判定在记账之后：到 80% 发一次 `BudgetWarning`，到 100% 把 Task 置为 `failed: budget_exhausted`、终止运行。〔读〕
- 记账本身有延迟：`llm-proxy` 把用量攒成批再报给内核，默认 2 秒冲一次（`llm-proxy/src/report.ts`）。〔读〕
  越线之后、运行被终止之前完成的调用都照样计入，所以超出的不只是一次在途调用（比遗留 367 说的那一种多）。
- 工作区每日 token 预算（`sumTodayTokensByWorkspace`）和目标预算用的是同一个求和口径。〔读〕
- 默认每个 Task 200,000（配额 `task.default_token_budget`，所有者可用 `set_quota` 改）；`invoke_worker` 没有预算参数；
  WorkerDefinition 上没有预算字段，只有目标计划里的 WorkerSpec 有 `tokenBudget`。〔读〕
- 花费另有一条线：每条用量按模型的费率算出 `cost_usd`（缓存读有单独的费率），工作区有日成本配额
  `task.daily_cost_budget_usd`，默认不设上限。〔读〕

### 1.4 为什么是平方

设起始上下文（系统提示词、工具定义、Skill、Worker 上下文）为 B，每次工具结果平均 r，一次运行调了 k 次模型。
第 i 次调用要把前面的全部内容再送一遍，所以累计用量约为 `k·B + r·k(k−1)/2`。

把主机上的数代进去（工具调用次数近似当作模型调用次数）：〔报〕〔推〕

| Task | 工具调用 | 用量 | 读法 |
|---|---|---|---|
| 完整容器排查 | 20 | 253,465（预算 200,000） | B 取 6,000 到 8,000 时，光 `k·B` 就是 12 万到 17 万；平均每个结果只需几百 token 就到 25 万 |
| 只查一个 compose 项目 | 11 | 超过 200,000 | 次数少而用量同样超线，说明平均每个结果大得多：反复拿到顶到上限的截断结果 |

两点读法：

- **大结果不是唯一的原因，甚至不是主要的。** 第一个 Task 里，即使每个工具结果都是零，20 次调用重读起始上下文也要用掉默认预算的六到八成。
  所以 966（门侧去掉 `labels`）必要但不够。
- **超出 26% 不是一次调用的量。** 25 万除以二十来次调用，平均每次一万二左右；超出的 5.3 万相当于三四次调用。〔推〕
  这个 Task 34 秒里调了二十来次，平均不到 2 秒一次，而用量 2 秒才报一批，再加上终止运行的延迟，越线后还能跑出好几次（§1.3）。

本线程核实时曾按「八次顶到上限的结果」推算，与 25 万的数字也吻合，但调用次数不对。967 登记行里的那半句以本节为准。

### 1.5 I18 写的和做的差在哪

设计文档 I18：「token 到 80% 时 `llm-proxy` 上报、内核经 `context` 注入警告，到 100% 时 `llm-proxy` 返回预算耗尽错误，
Worker 本轮结束」。实现里：〔读〕

- 80% 的警告只进了**发起调用的入口智能体**的上下文（`application/linkage/budget-consumer.ts`），Worker 收不到；
- 100% 时 `llm-proxy` 的拒绝只对工作区级预算生效（`/internal/llm-budget-exhausted`），Task 级是内核事后判定加终止运行；
- Worker 被终止后 Task 没有结果。它报告过的工具调用还在（遗留 155 的记录），所以证据没丢，结论丢了。

## 2. 领域模型（只列本次涉及的）

| 概念 | 是什么 | 谁是真相源 | 本文改不改 |
|---|---|---|---|
| 门回答 | 目标系统经门给出的完整回答 | 门 | 不改；回哪些字段由门定（966 与 §5 的约定） |
| 观察事实 | 内核按 `result_mapping` 从门回答写出的事实 | 内核 | 不改 |
| 模型可见结果 | 门回答进入模型上下文的那一份 | 平台扩展 | 改：按项截断加说明（§4.1） |
| 用量 | 一次模型调用实际发生的四种 token 数 | `llm-proxy` 上报，内核记录 | 不改 |
| 计入预算的量 | 治理对用量的折算，用来和预算比 | 内核 | 新增（§4.3） |
| 预算 | 一个 Task 最多可以计入多少 | 所有者：配额、WorkerDefinition、目标 | 改：多一个声明的位置（§4.5） |

要守住的几条：

- **N1** 模型可见结果被截短时，模型一定被告知哪些列表不全、各看到几项共几项。不存在「不全但没说」的结果。
- **N2** 观察事实来自完整的门回答，与模型看到多少无关（现状如此，写下来防回退）。
- **N3** 用量是事实，不因治理口径改变而改写；计入预算的量由用量按一个函数算出，三处预算用同一个函数。
- **N4** 预算只由人的治理动作决定（配额、发布定义、确认或修订目标）。智能体的任何调用参数都不能抬高自己或下游的预算。
- **N5** 预算用尽之前，Worker 至少被提示一次还有多少余量。
- **N6** 说明行是平台的话，里面不出现门回答里的值；路径里不是普通标识符的键写成位置。

## 3. 候选与取舍

| 候选 | 取舍 |
|---|---|
| 只调大默认预算 | 不解决平方增长，只是把墙往后挪；长一点的任务照样撞。可以作为换计法之前的临时手段，由所有者按工作区调配额 |
| 取消 Task 级硬上限 | 不采纳。脚本化重放或模型打转时没有东西拦；工作区日成本默认还是不设上限的 |
| 用 `result_mapping` 的映射结果当模型视图 | 不采纳。它是「写成哪些事实」的投影，按标识与新鲜度选字段；排查要看的字段是另一回事。没有映射的 Operation（`compose.ls`、`logs_tail`、检索）也就没有视图。两种投影各管各的 |
| 内核给列表结果加统一信封（`items`、`total`、`nextCursor`） | 不采纳。要改每个 Operation 的结果形状和映射路径，门实例的定义摘要跟着变，主机上要逐个确认。单次回答的项数平台扩展自己数得出；跨页的总数只有目标系统知道，原样透传 |
| 把预算单位直接换成美元 | 不采纳为主路径。没有配置费率的模型 `cost_usd` 是空的。花费这条线已经有日成本配额，继续由它管 |
| 被截掉的部分由平台扩展留着，给模型一个「取下一段」的工具 | 现在不做。每取一段都再进一次上下文；大列表的正路是在源头缩小范围。目标系统确实不能过滤的情形出现了再做（§10） |
| 运行中挂起等所有者批准续额 | 列为备选，不建议（§4.6） |

## 4. 目标方案（Target Architecture）

### 4.1 给模型的结果：紧凑、按项截断、说明截掉了什么（阶段 1）

改的只有 `truncateToolResult` 这一个函数和它的三个调用点，三种模式一起受益。

1. **序列化不缩进。** 嵌套结构上省两到三成字符。〔推〕不超过上限的结果除此之外逐字不变，不加任何说明行。
2. **超过上限时只截整项。**
   - 很长的字符串值留头和尾，中间换成一句「省略了 N 个字符」。日志的最新部分因此保留。
   - 还超，就从最大的数组起从末尾去掉整项，直到放得下。每个被截的数组记下路径、留了几项、原有几项。
   - 仍放不下（一个巨大的单项、极深的嵌套）才退回现在的按字符截断，说明行如实写「以下不是完整的 JSON」。
3. **说明行写三件事**：哪些路径不全、各留了几项共几项（或字符数）；不要把看到的当成全部去计数或下结论；
   这个 Operation 接受哪些参数可以用来缩小范围（取自它的 `params_schema` 的属性名），没有的话就让模型在结果里写明列表不全。

要守住的性质（验收按这些写测试，不规定实现）：

- 输出不超过上限加一个有界的说明行；
- 除最后那种退路外，正文能被解析成 JSON；每个留下的数组是原数组的前缀；说明行里的数字准确；
- 同样的输入得到同样的输出；
- 说明行不含门回答里的值（N6）。

上限的数值 16,000 字符先不动。不缩进之后同样的上限能装下更多内容。

### 4.2 软着陆：Worker 在到线前被提示收尾（阶段 1）

- 平台扩展在每次模型调用前要知道两个数：这个 Task 的预算和已经计入的量。预算从 `get_task` 读（它已经带 `tokenBudget`，
  Worker 的 Handle 本来就持有这个能力）。已计入的量有两个来源，由 pi 席位定：
  用 pi 事件里每次调用的用量在本地累加（没有延迟，首选，要先确认 pi 1.1.0 的事件里带四种 token 数）；
  或者每次调用前再读一次 `get_task` 的 `tokensUsed`（内核的数，但比实际晚一批上报，§1.3，用它时下面的倍数要取大）。
  要求是每次模型调用最多一次内核读取，读不到就不提示，不影响运行。
- **提示的时机按上一次调用的大小预测，不按固定百分比。** 当「剩余量小于上一次调用计入量的若干倍」时提示
  （本地累加时取 3 倍，读内核的数时取 5 倍，实现时按实测调）。
  理由：越到后面每一步越贵，而且上报这一步自己也要再读一遍全部上下文；按固定的 80% 提示，在长运行里常常只剩一两步的余量。
- 提示作为末尾一条不进缓存的短消息加进去（入口模式的现场上下文已经是这个做法，`prompt-cache.ts`），不破坏已缓存的前缀。
  内容是：余量不多了，现在就用手上的结论调用 `report_result`，把没查到的写进 `findings`。
- 内核 100% 的硬停照旧，是兜底。80% 给入口智能体的那条警告照旧。

效果是多数会撞线的运行变成「完成，结论里写明哪些没查」，不再是失败且没有结果。
结果契约暂不加「未完成」字段，先看提示后的行为；要加时走线上契约的评审。

### 4.3 计法：用量与计入预算的量分开（阶段 2）

定义一个折算函数，只在一处：

```
计入预算的量 = 输入（净值） + 输出 + 缓存写入 + 缓存重读 × w        w 默认 0.1（V1）
```

- `tasks.tokens_used` 保持原义（四项全额相加），控制台照旧显示；新增一列计入预算的量，预算判定、80% 警告、
  目标对各步的汇总都改用它。工作区每日 token 预算的求和用同一个 w。三处不许各写各的（N3）。
- 线上契约里 Task 多一个字段。控制台把两个数都显示出来，并写明其中多少是重读，否则所有者会看到
  「用了 25 万、预算 20 万、却没有停」而不明白。
- 升级时已有的行把新列回填成 `tokens_used`（偏保守，不会让在途的 Task 突然多出余量以外的行为）。
- 不提供缓存的模型没有重读这一项，计入量等于用量，和今天一样。这是对的：那种情况下每一步确实都要重新付全价，
  对它们起作用的是 §4.4 的折叠和 §4.5 的档位。

按这个计法重算 §1.4 的第一个 Task：新增部分约 2 到 3 万，重读约 22 万折成 2.2 万，合计约 5 万，是默认预算的四分之一。〔推〕
同样的 200,000 大约能做三倍多的工作，而一个打转的 Worker 仍然会被停住。

这一步放宽了「同一个预算数能花多少钱」。真正管钱的应当是工作区日成本配额，它默认不设上限（V3）。

前提要核对一件事：主机上这类 Task 的用量记录里缓存重读是不是非零。是，本节按上面生效；不是，说明缓存没命中，
要先查缓存为什么没命中（Worker 上下文已经按可缓存的位置放了，`modes/worker.ts` 的 `withWorkerContextFirst`）。

### 4.4 旧工具结果成批折叠（阶段 3）

- 平台扩展在组装上下文时，把较早的工具结果换成一行占位：哪个工具、原来多少字符、需要的话再调一次。最近的几个结果不动。
- **成批做，不逐轮做。** 改动历史中间的内容会让它后面的缓存全部失效、按写入重算一次。所以只在上下文超过一个门槛、
  而且一次能折掉足够多的时候做一批；折过的不再变，之后的前缀重新稳定。规则必须只由历史决定，每次调用算出来的结果一致。
- 它和 §4.3 部分互相替代：换计法以后重读只按一成计，折叠在预算上的收益变小，主要价值是不撞模型的上下文窗口、
  以及在不提供缓存的模型上省真钱。所以排在阶段 2 之后，门槛按阶段 2 之后的实测定。
- 折叠掉的内容并没有丢：门调用的 Observation 和 Worker 报告的工具调用记录都在内核里。

### 4.5 预算在哪声明、谁能改（阶段 4）

- WorkerDefinition 的内容多一个可选的 `tokenBudget`，与目标计划 WorkerSpec 里已有的同名字段同一个意思。
  定义由人发布，所以这是一次治理动作；智能体只能提议定义，不能发布。
- 新配额 `task.max_token_budget`：工作区里任何定义、任何一步能声明的上限。
- 一个 Task 的预算取：定义声明的值，没有就用 `task.default_token_budget`；不超过 `task.max_token_budget`；
  在目标里再不超过目标剩余的量（现有逻辑）。`invoke_worker` 仍然没有预算参数（N4）。
- 控制台发布定义时给三档预设加自定义，不让人手打一个裸数。数值是产品默认，建议 200,000、600,000、2,000,000，
  上限配额默认等于最高一档。内置包的 Worker 文件可以带这个字段，安装审阅时显示。
- **长任务的位置是目标。** 目标有整体预算和墙钟，每一步是有界的 Task；预算用尽时目标进入 `paused(budget_exhausted)`，
  请求人用 `revise_goal` 改预算、`resume_goal` 恢复。〔读〕「到线后由人决定要不要继续」在目标这一层已经是现成的状态机，
  不需要在单个 Task 里再造一遍。

### 4.6 到线之后：续作，而不是挂起（V2）

| | A 软着陆加续作 Task（默认） | B 运行中挂起等批 |
|---|---|---|
| 做法 | Worker 按 §4.2 交出部分结果，Task 正常完成；人或入口智能体看了结果说继续，再委派一个 Task，输入里带上已有结论和没做完的部分 | 到线时 Task 进入一个新的等待状态，所有者批准追加预算后原运行继续 |
| 要新造的 | 没有新状态；可选地在新 Task 上记一条「接续自哪个 Task」的关系 | 新状态和它的迁移、一种新的审批对象与控制台入口、等待期间容器是留着（占资源，墙钟照走）还是做会话恢复 |
| 人在哪里把关 | 每一段都有界；继续与否是一次明确的委派 | 一次批准 |
| 失败时 | 部分结果已经落库 | 批准迟迟不来时还是要有超时与收尾 |

建议 A。B 的价值是省掉重新进入上下文的那点开销，代价是一整套新的状态与恢复机制，而目标那一层已经提供了「暂停、改预算、恢复」。

### 4.7 硬停超出多少

超出的量是越线之后、运行被终止之前完成的所有调用：在途的那一次，加上用量还没报到内核的那一批（默认 2 秒），
再加上终止运行本身的延迟。调用越快、每次越贵，超得越多；§1.4 的例子里是预算的四分之一。目标定为「超出不超过一成」。

- 换计法（§4.3）之后，每次调用的计入量是它新增的部分加一成的重读，同一个例子里一次只占预算的百分之一二，
  越线后多跑三四次也在一成以内。〔推〕软着陆（§4.2）让多数运行根本到不了线。
- 仍然超的（不提供缓存的模型、很快的模型），在第一手记账的地方拦：`llm-proxy` 是每次调用最先知道用量的一方，
  让它知道这个会话的预算，自己累加，到线就不再转发、返回预算耗尽；平台扩展收到后用已有的兜底上报收尾。
  这正是 I18 原文「到 100% 时 `llm-proxy` 返回预算耗尽错误」，现在只在工作区级做了。内核的事后判定留作兜底
  （`llm-proxy` 重启会丢内存里的累计）。它怎么得知预算（随 Handle 带出，或会话第一次调用时向内核问一次）由实现定。
  列为阶段 5，阶段 2 之后实测仍超一成再做。

## 5. 和 966、968 对齐的口径

**966（门侧投影）与本文的分工**

- 966 只改门：列表类 Operation 回摘要字段，大块的附属结构只在单项读取里回。它不动 `platform-extension`；
  「给模型的 JSON 不缩进」放在本文阶段 1，这样 966 是一个只涉及门的 PR。
- 由 966 立下、以后每个内置门照做的约定：
  1. 列表类默认回摘要：标识加排查用得到的状态字段；
  2. 目标系统支持时提供缩小范围的参数（按状态、按名字、分页），并在 Operation 描述里写出来；
  3. 每个内置门带一个「载荷预算」测试：用一份有代表性的夹具（docker 门建议 40 个容器、带真实长度的名字与镜像名），
     断言列表类结果序列化后不触发截断。门槛由 966 的作者按实测定，写进测试。
- docker 门要加过滤参数（例如按状态）会改 `params_schema`，门实例的定义随之变化，主机上要确认一次。
  不单独为它开主机步骤，和下一次 docker 清单的改动合在一起。

**968（本体词汇进 Worker 上下文）要守的预算**

词汇放在 Worker 上下文里，是每次调用都要重读的固定部分，直接加在 §1.4 的 B 上。所以：

- 词汇段有上限，建议 4,000 字符；
- 先放与这个 Worker 相关的：它能调用的 Operation 的 `reads` / `writes` 里出现的对象类型，以及两端都在其中的 LinkType 签名；
  放不下的其余部分只列名字，再放不下就只给个数；
- 一行一个 LinkType 签名、一行一个对象类型与它的标识键，不放属性的完整定义。

同一段里的「相关事实」（`search` 默认最多 50 条，逐条序列化）今天没有上限，随 968 一起给一个。〔读〕

## 7. 验证

- **阶段 1**：截断函数按 §4.1 的性质写属性测试；worker 模式的 SDK 测试里放一个 18 项的列表，断言模型看到的是合法 JSON 加
  「共 18 项」；`logs_tail` 超长时留下的是尾部；说明行不含夹具里的任何值。软着陆用脚本化模型跑一个预算很小的 Task，
  断言结果是 `completed` 且 `findings` 里有未完成的说明，而不是 `budget_exhausted`。
- **阶段 2**：同一组用量记录，Task、目标、工作区每日三处算出的计入量一致（一个测试喂同一份记录给三条路径）；
  没有缓存重读的记录，计入量等于用量；回填后在途 Task 的判定不变。
- **真实模型一轮**：阶段 0 和 1 合入后，在 staging 用真实模型把「完整容器排查」跑一次，记下工具调用次数、用量、
  缓存重读占比、是否完成。计入付费额度，量级是一个 Task。阶段 2 之后同一任务再跑一次，核对 §4.3 的估算。
- **主机**：升级后在试验工作区重跑清单里的三个任务，结果进主机升级报告。

## 8. 风险与代价

- **放宽了单个 Task 能花的钱。** 同一个预算数在新计法下能跑更久。对策是 V3 的日成本配额；公开文档不写数值。
- **两个数并存会让人困惑。** 控制台必须同时给出用量和计入量并说明差别，否则是新的「看不懂」。
- **软着陆依赖模型听话。** 模型可以无视提示继续调用工具；那时硬停仍然兜底，结果和今天一样。
- **折叠可能折掉模型还要用的内容。** 占位行写明可以再调一次；门槛宁可保守。阶段 3 在阶段 2 的数据出来前不动。
- **按项截断改变了模型看到的文本形状。** 脚本化的验收里有断言工具结果原文的，要一起改。
- **w 是一个产品常量，不是事实。** 不同模型的缓存读费率不同。取一个固定值是为了让预算数字可解释；
  要精确到钱，看的是 `cost_usd`。
